# ADR 0004 — Domain events, commands & write atomicity

- **Status:** Aceita
- **Data:** 2026-06-23
- **Contexto:** Rota Saúde

## Decisão

A orquestração do domínio segue uma regra única:

> Comandos mudam estado e publicam eventos; eventos disparam efeitos colaterais (jobs).

Três mecanismos a sustentam:

1. **Commands** — toda mudança de estado relevante é um Command Object que devolve
   um `Result`, roda em transação e publica eventos.
2. **Domain events** — um padrão **outbox-leve sobre Postgres**: a tabela
   `domain_events` é trilha de auditoria imutável e fonte de replay; um publisher
   único enfileira consumidores via bindings declarativos.
3. **Atomicidade write+enqueue** — `enqueue_after_transaction_commit = :always`: um
   job só fica visível ao worker depois do COMMIT; em ROLLBACK, nunca é enfileirado.

## Detalhamento

**Tabela `domain_events`** (imutável; único UPDATE legítimo é `published_at`):

| coluna | tipo | nota |
|---|---|---|
| `id` | uuid | PK |
| `event_id` | uuid | id estável do evento; chave de idempotência (ADR 0005) |
| `name` | string | `triage.completed`, `consent.given`, ... |
| `municipality_id` | bigint **null** | tenant; null só para auditoria platform-scope (ADR 0014) |
| `payload` | jsonb | dados imutáveis |
| `occurred_at` | timestamptz | UTC |
| `published_at` | timestamptz null | quando os bindings foram disparados |

**Publisher.** A API única é `DomainEvents.publish(event_name, **payload)`. Ela lê o
tenant de `Current.municipality_id` (já escopado pelo `around_action` web ou pelo
`with_tenant` de um job) e levanta `TenantMissing` se for nulo. Gera um `event_id`
estável, insere a linha em `domain_events` carimbando `municipality_id`, `payload` e
`occurred_at`, e então percorre os bindings registrados para aquele evento,
enfileirando cada job com `event_id`, `event_name`, `municipality_id` e `payload`
como argumentos literais. O insert de auditoria e os enfileiramentos acontecem no
mesmo átomo lógico. O identificador do agregado, quando o consumidor precisa dele,
viaja **no `payload`** (ex.: `triage_id`).

`published_at` separa "evento registrado" de "consumidores notificados"; é
atualizado best-effort quando o consumidor termina, e habilita o replay (ADR 0014).

**Bindings declarativos** em `config/initializers/domain_events.rb`, lidos uma vez
no boot. Cada binding mapeia um nome de evento aos seus consumidores:
`inbound_message.received` aciona o `ProcessInboundMessageJob`; `triage.completed`
aciona `GenerateReportJob`, `UpdateDashboardJob` e `NotifyCitizenJob`;
`triage.urgent` aciona o `AlertMunicipalityJob`; `consent.given` e `consent.revoked`
não têm consumidores hoje (só auditam). Adicionar consumidor é uma linha mais o
`queue_as` no job; remover é apagar a linha — a auditoria permanece.

**Atomicidade.** `config.active_job.enqueue_after_transaction_commit = :always` em
`config/application.rb`. Exceção (job que não toca estado de domínio e é seguro com
rollback, ex.: telemetria pura) é código explícito no call-site, nunca default.

**Commands.** Cada comando é uma classe em `app/commands/` com `.call(**) -> Result`
como ponto único de entrada. O caso canônico, `CompleteTriage`, recebe `triage:` e
`answer:`: falha cedo com `Result.fail(:no_consent)` se a conversa não consentiu e
`Result.fail(:already_completed)` se a triagem já terminou; dentro de
`triage.with_lock`, avalia o protocolo (ADR 0009) sobre as respostas acumuladas,
registra a resposta, completa a triagem quando o `Outcome` é terminal, e publica
`triage.completed` (sempre que terminal) e `triage.urgent` (quando o tier exige
alerta); ao fim devolve `Result.ok(triage:, outcome:)`.

`Result` é um Value Object imutável: `Result.ok(payload)` e
`Result.fail(:reason, message:, details:)`, com a API mínima `ok?` / `failure?` /
`reason` / `payload` / `to_h`. O controller traduz `Result` em HTTP; o job traduz em
log + retry. A tradução fica **fora** do comando.

Comandos iniciais (nomes em inglês — ADR 0001):

| Command | Entradas | Eventos publicados |
|---|---|---|
| `CompleteTriage` | `triage:, answer:` | `triage.completed`, `triage.urgent` |
| `GiveConsent` | `conversation:, version:, evidence:` | `consent.given` |
| `RevokeConsent` | `conversation:` | `consent.revoked` |

`IngestInboundMessage` **não** é comando: a borda do WhatsApp (ADR 0007) faz o
`INSERT` direto e publica `inbound_message.received` — é registro de fato, sem
decisão de domínio, e precisa de ack rápido.

**Nomenclatura de eventos:** minúsculo, `<agregado>.<ação_passado>`
(`triage.completed`), nunca o nome do consumidor; payload só com dados (nunca objetos
AR), incluindo o id do agregado quando o consumidor precisar dele (ex.: `triage_id`).

## Invariantes

- `domain_events` é imutável — único UPDATE legítimo é `published_at`.
- `publish` exige tenant setado (`TenantMissing` se nulo); o evento e cada job
  carregam `municipality_id` literal.
- Nenhum job é enfileirado antes do COMMIT; em ROLLBACK, nenhum efeito externo
  dispara.
- Comando devolve `Result` sempre — nunca `nil`, nunca AR direto, nunca `raise` para
  falha esperada.
- Comando roda em transação e **não** chama HTTP (efeito externo é job — ADR 0005).
- Ordem é garantida **dentro** de um agregado (via transação), não global entre
  agregados.

## Consequências

- Comandos ficam limpos: publicam um evento, ponto; consumidores são detalhe de
  infra.
- Auditoria por construção — `SELECT * FROM domain_events WHERE municipality_id = ?`
  (filtrando por `name` ou por campo do `payload`, ex.: `payload->>'triage_id'`) é a
  história.
- Novo consumidor não toca o comando — só o initializer; replay vira query sobre
  `published_at IS NULL` (ADR 0014).
- O custo do `publish` (1 insert + N enqueues, carimbados) cresce com o número de
  consumidores; aceitável.
- `published_at` é best-effort: se o worker cair entre dispatch e update, o evento
  parece pendente e pode ser reenfileirado — por isso os consumidores são
  idempotentes (ADR 0005).

## Relacionado

- ADR 0003 — o tenant que `publish` carimba e que o job aplica.
- ADR 0005 — consumidores idempotentes e efeito externo fora do lock.
- ADR 0006 — as filas onde os jobs caem.
- ADR 0009 — `CompleteTriage` chama o motor de protocolos (`evaluate -> Outcome`).
- ADR 0014 — `domain_events` como log de auditoria, retenção e replay.

## Em aberto

- Versionamento de schema de payload (sufixo `.v2` ou `schema_version` no payload)
  quando um evento mudar de forma.
- Particionar `domain_events` por mês se o volume passar de ~10⁷ linhas/mês por
  município.
