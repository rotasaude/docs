# ADR 0002 — Repository topology (multi-repo)

- **Status:** Aceita
- **Data:** 2026-06-23
- **Contexto:** Rota Saúde

## Decisão

O Rota Saúde é organizado em **múltiplos repositórios, um por aplicação**, sob a
organização `rotasaude/`. Cada app tem deploy, time e permissões independentes — a
força que governa a topologia é a **autonomia operacional por aplicação**. As
aplicações **compartilham contratos, não implementação**: o que une o produto é um
repositório de contratos neutros e o corpus de governança, nunca código
compartilhado.

| Repo | Papel | Plano de dados |
|---|---|---|
| `api` | Backend Rails (papéis web + worker) | — |
| `admin` | Frontend da plataforma, cross-tenant | `rota_admin` (BYPASSRLS) |
| `dashboard` | Frontend da cidade, tenant-scoped | `rota_app` (RLS) |
| `wpda` | Frontend do paciente, público (token assinado), tenant-scoped | `rota_app` (RLS) |
| `contracts` | Contratos: events, protocols, types, design-tokens | — (nunca carrega secret) |
| `docs` | Governança: ADRs, módulos, ciclo, operação | — |
| `.github` | Templates de issue e workflows reutilizáveis da org | — |

Board de execução: **Project v2 no nível da organização**, agregando issues de
todos os repos. Não é repositório.

## Detalhamento

**Três frontends separados** (não um console único) porque os papéis têm fronteiras
de segurança e privacidade intransponíveis:

- `admin` lê dado cross-tenant sob `rota_admin` e aciona custódia de secrets
  de todas as cidades (ADR 0013). Vazamento aqui afeta o piloto inteiro.
- `dashboard` lê dado de **uma** cidade sob RLS (ADR 0003). Vazamento se restringe
  àquela cidade — diferença de ordem de grandeza para LGPD.
- `wpda` é a única superfície pública (sem login institucional; auth por token
  assinado). Superfície de ataque distinta — CSP, headers e auth próprios.

Apps separados eliminam por construção o risco de vazar caminho administrativo para
a internet por roteamento equivocado.

**`contracts` compartilha contrato, não código:**

```
contracts/
├─ events/         # formato dos domain events (ADR 0004)
├─ protocols/      # JSON Schema da definição de protocolo (ADR 0009)
├─ types/          # contrato de tipos Ruby ↔ TS
└─ design-tokens/  # cores, espaçamento, tipografia como dado (JSON / CSS vars)
```

O design system é compartilhado **como tokens** (dado), não como biblioteca de
componentes: cada frontend implementa seus próprios componentes consumindo os mesmos
tokens. Trocar a cor da marca é editar um JSON, sem rebuild cruzado. A política de
versionamento de `contracts` vive no ADR 0015.

**Como a unidade do produto sobrevive sem repo único** — cinco camadas, nenhuma de
código compartilhado: `contracts` (mesma língua de dados e design), `docs` (mesmas
decisões — o ADR 0003 vale para qualquer app que toque o banco), board da org (uma
funcionalidade com tarefas-filhas em repos diferentes numa tela), `.github` da org
(mesmos templates e gates de CI herdados), convenção de nome e versão.

## Invariantes

- Aplicações compartilham **contrato**, nunca implementação (um componente React ou
  classe Ruby não atravessa repos).
- `contracts` **nunca** contém secret, chave ou credencial.
- O deploy do `admin` é isolável da internet pública; nunca roteável a
  partir das superfícies de cidadão.
- Cada app tem deploy, permissão e ciclo de release independentes.

## Consequências

- Mudança de design global fica mais lenta: cada frontend consome `design-tokens` no
  seu ritmo; pode haver janela de dessincronia visual. É o trade-off por autonomia.
- ADR e código vivem em repos distintos; o PR que implementa um ADR o referencia por
  **URL**, não por path relativo.
- Setup inicial multiplicado (6 repos = 6 CIs, 6 branch protections); mitigado por
  workflows reutilizáveis no `.github` da org — o pipeline é escrito uma vez e
  herdado.
- Contrato exige disciplina de versão; mal versionado, quebra apps em silêncio —
  mitigado pelo ADR 0015.

## Relacionado

- ADR 0001 — o stack do `api`.
- ADR 0003 — RLS independe da topologia de repo; vale para qualquer app que toque o
  banco.
- ADR 0013 — custódia de secrets por repo; a chave de criptografia vive só no env do
  `api`.
- ADR 0015 — política de versionamento de `contracts`.

## Em aberto

- Nome definitivo da organização (`rotasaude/` ou conta existente com prefixo).
- Preservação de histórico do `api` na extração para repo próprio (filter-repo vs
  tag-e-recomeço no piloto).
- Estratégia de release coordenado quando uma funcionalidade atravessa repos.
