# ADR-0020 — Tenant em eventos e jobs (emenda aos ADR 0003 e 0005)

* Status: Aceita
* Data: 2026-06-20
* Contexto: Rota Saúde (piloto municipal)
* Emenda: ADR 0003 (`DomainEvents.publish`), ADR 0005 (`IdempotentConsumer`)
* Relacionado: ADR 0019 (RLS, variável de tenant), ADR 0009 (auditoria), ADR 0006 (commands), ADR 0010/0014 (jobs de ingestão).

## Contexto
Sob RLS (0019), toda query de domínio precisa de `app.municipality_id` setado. No caminho web isso vem do `around_action`. No worker não há request: o job roda depois, isolado. E há um problema de bootstrap — descobrir o tenant do job buscando no banco já estaria sob RLS. Logo, `municipality_id` precisa ser dado literal que viaja com o evento/job, não algo que se consulta.
`Current` aqui é um `ActiveSupport::CurrentAttributes` (`Current.municipality_id`), resetado por request e por execução de job.

## Decisão
`municipality_id` é carimbado no `publish` (lido do ambiente já escopado) e propagado como argumento até o `perform`, onde o job seta `SET LOCAL` antes de tocar o banco.

### Emenda ao ADR 0003 — `publish` carimba o tenant
No `publish`, o tenant já está setado (o command roda dentro do `around_action` web ou do `with_tenant` de um job de ingestão). O `publish` lê do `Current` e injeta em cada job e na linha de auditoria — os call sites não mudam.

```ruby
# app/events/domain_events.rb  (substitui o publish do ADR 0003)
def self.publish(event_name, **payload)
  event_id        = SecureRandom.uuid
  municipality_id = Current.municipality_id
  raise TenantMissing, "publish sem tenant setado" if municipality_id.nil?

  # auditoria (0009), mesma transação — ver nota §1.3
  DomainEvent.create!(
    event_id:, name: event_name.to_s, payload:,
    municipality_id:, occurred_at: Time.current
  )

  registry[event_name.to_s].each do |sub|
    job = sub.queue ? sub.job.constantize.set(queue: sub.queue) : sub.job.constantize
    job.perform_later(event_id:, event_name: event_name.to_s, municipality_id:, payload:)
  end
  event_id
end
```

**Nota (§1.3 da revisão).** O 0009 já decidira inserir em `domain_events` no mesmo `publish`, mas o código do 0003 nunca refletiu isso. Este `publish` é a forma autoritativa: carrega o insert do 0009 e o `municipality_id`. Quem implementar segue este, não o trecho do 0003.

### Emenda ao ADR 0005 — consumer seta o tenant antes de tudo
Um concern compartilhado seta `Current` + `SET LOCAL` dentro de transação. Vale para consumers de domínio (via `IdempotentConsumer`) e para jobs operacionais que tocam dado de tenant sem serem consumers (`ProcessInboundMessageJob`, `SendWhatsappJob`).

```ruby
# app/jobs/concerns/tenant_scoped_job.rb
module TenantScopedJob
  extend ActiveSupport::Concern

  private

  def with_tenant(municipality_id)
    raise TenantMissing if municipality_id.nil?
    ApplicationRecord.transaction do
      Current.municipality_id = municipality_id
      ApplicationRecord.connection.execute(
        ApplicationRecord.sanitize_sql(["SET LOCAL app.municipality_id = ?", municipality_id])
      )
      yield
    end
  end
end
```

```ruby
# app/jobs/concerns/idempotent_consumer.rb  (substitui o do ADR 0005)
module IdempotentConsumer
  extend ActiveSupport::Concern
  include TenantScopedJob

  def perform(event_id:, event_name:, municipality_id:, payload:)
    with_tenant(municipality_id) do
      ProcessedEvent.create!(event_id:, consumer: self.class.name, municipality_id:)
      handle(**payload.symbolize_keys)
    end
  rescue ActiveRecord::RecordNotUnique
    # entrega duplicada desta combinação evento+consumer — no-op
  end
end
```

`processed_events` ganha `municipality_id` (escopado por RLS, consistente), mas o índice único permanece `(event_id, consumer)` — `event_id` é UUID global e cada evento pertence a um município, então não há colisão entre tenants. O `municipality_id` é para escopo/auditoria, não para unicidade.

### Jobs de ingestão (0010/0014) também escopam
`ProcessInboundMessageJob` e `SendWhatsappJob` não são consumers de domínio, mas tocam dado de tenant — o primeiro avança a conversa, o segundo lê a credencial WhatsApp do município (0024). Ambos recebem `municipality_id` como argumento (resolvido na ingestão, ADR 0021) e abrem com `with_tenant`. Para o `ProcessInboundMessageJob`, o `with_tenant` encapsula a transação que já existia em volta do `with_lock`.

### Interação com a idempotência (§1.2 da revisão)
Envolver `create!` + `handle` numa transação (exigência do `SET LOCAL`) muda a semântica que o 0005 tinha:

* Handler de efeito em banco (`UpdateDashboardJob`): se `handle` levanta, a transação dá rollback junto com o `ProcessedEvent.create!` → o retry re-executa. Vira at-least-once correto. Resolve, de lado, a metade do §1.2 que era em banco.
* Handler de efeito HTTP (`NotifyCitizenJob`, `AlertMunicipalityJob`): a chamada externa não dá rollback. Persiste o problema do §1.2 — invertido (possível reenvio em vez de envio perdido). Continua precisando de idempotency key no provedor ou marcador pós-confirmação.

Este ADR não fecha o §1.2 para o caso HTTP — é decisão à parte. Apenas registra que o wrapper de RLS altera o comportamento e que o caso HTTP segue aberto.

## Consequências

* O custo do `publish` cresce de novo (1 insert + N enqueues, agora carimbados) — acoplamento crescente já apontado (§3.2 da nota). Aceitável; documentado.
* Qualquer job que toque domínio tem que incluir `TenantScopedJob` e receber `municipality_id`. Um job que esqueça falha fechado (sem tenant → query levanta), não vaza — RLS é a rede.

## Em aberto

* §1.2 para efeito HTTP (idempotency key no provedor WhatsApp / Meta): ADR à parte, no escopo de confiabilidade de entrega, não de tenant.
