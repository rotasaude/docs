# ADR 0018 — Topologia física do monorepo: 4 apps, deploy por ambiente

- **Status:** Aceita
- **Data:** 2026-06-18 (proposta inicial), ratificada 2026-06-23
- **Contexto:** Rota Saúde (piloto municipal)
- **Emenda:** ADR 0002 (estrutura de aplicações); toca ADR 0001 (deploy/Kamal)
- **Relacionado:** ADR 0011 (chaves/secrets), ADR 0016 (storage da definição
  de protocolo em banco), ADR 0019 (RLS — `rota_app` vs `rota_admin`), ADR 0022
  e 0023 (papéis de usuário que distinguem as superfícies)

> O 0002 decidiu **dois papéis a partir de uma imagem** e manteve `packages/`,
> mas descreveu o app Rails com caminhos root-relative (`app/jobs/...`). Esta
> emenda **não muda papéis nem imagem** — muda **onde os arquivos moram**,
> **como o deploy é organizado por ambiente**, e **separa o frontend em três
> aplicações** com papéis distintos. Decisões aceitas são imutáveis; o 0002
> não é reescrito, esta emenda passa a ser a fonte da verdade do layout
> físico.

## Decisão

Layout de topo do monorepo:

```
rota-saude/
├─ apps/
│  ├─ api/             # backend Rails 8 (papéis web + worker, mesma imagem)
│  │  ├─ app/ config/ db/ bin/ Dockerfile
│  │  └─ deploy/{development,production}/
│  ├─ admin-console/   # frontend — plataforma, cross-tenant
│  │  ├─ src/ package.json
│  │  └─ deploy/{development,production}/
│  ├─ dashboard/       # frontend — cidade, tenant-scoped
│  │  ├─ src/ package.json
│  │  └─ deploy/{development,production}/
│  └─ wpda/            # frontend — paciente, tenant-scoped
│     ├─ src/ package.json
│     └─ deploy/{development,production}/
├─ packages/           # compartilhado na raiz (ui, types, protocols)
├─ docs/
│  ├─ adr/             # ADRs (este arquivo vive aqui)
│  ├─ modulos/         # mapa de módulos (ver docs/modulos/README.md)
│  └─ operacao/        # runbooks operacionais
└─ scripts/            # operação one-off
```

Regras:

1. **Backend** Rails vive em `apps/api/` — **não na raiz**.
2. **Frontend em três apps separados**, cada um com seu papel:
   - `admin-console/` — plataforma (`platform_operator`), cross-tenant, opera
     contra `rota_admin` (BYPASSRLS, ADR 0019). Provisiona cidade, custódia de
     chave, gestão de operadores, visão agregada cross-tenant.
   - `dashboard/` — cidade (`municipal_admin`, `viewer`), tenant-scoped, opera
     contra `rota_app` (RLS). Operação visível para o setor de saúde da cidade.
   - `wpda/` — paciente (sem login; token assinado), tenant-scoped, opera
     contra `rota_app` (RLS). Resultado de diagnóstico, ficha de
     acompanhamento, agendamento, jornada do cuidado.
3. **Deploy versionado por ambiente**: `deploy/development/` e
   `deploy/production/` dentro de cada app.
4. **Documentação** em `docs/`, dividida em `adr/` (decisões),
   `modulos/` (mapa de módulos do ciclo de desenvolvimento) e
   `operacao/` (runbooks).
5. **Scripts** de operação one-off em `scripts/`.
6. **`packages/` permanece na raiz** (compartilhado por `api` e pelos três
   frontends).

## Por que três frontends em vez de um console único

Três papéis distintos com **fronteiras de segurança e privacidade
intransponíveis**:

- `admin-console` lê dado cross-tenant sob `rota_admin` e custodia secrets de
  todas as cidades. Vazamento aqui afeta o piloto inteiro.
- `dashboard` lê dado de **uma** cidade sob RLS. Vazamento se restringe àquela
  cidade — e isso é diferença de ordem de grandeza para LGPD.
- `wpda` é a única superfície pública (sem login institucional). Superfície
  de ataque distinta; CSP, headers, e auth por token assinado têm requisitos
  próprios.

Misturar tela já seria erro de modelagem; misturar **deploy** introduz risco
de vazar caminho administrativo (rota `admin-console`) para a internet via
roteamento equivocado. Apps separados eliminam esse risco por construção.

## Re-parenting dos caminhos do ADR 0002

Todo caminho root-relative do 0002 ganha o prefixo `apps/api/`. Os exemplos do
0002 **não** são reescritos (imutável); esta tabela é a tradução autoritativa:

| ADR 0002 (root-relative) | ADR 0018 (atual) |
|---|---|
| `app/jobs/generate_report_job.rb` | `apps/api/app/jobs/generate_report_job.rb` |
| `app/events/domain_events.rb` | `apps/api/app/events/domain_events.rb` |
| `config/initializers/domain_events.rb` | `apps/api/config/initializers/domain_events.rb` |
| `bin/jobs` | `apps/api/bin/jobs` |
| (raiz) `Dockerfile` | `apps/api/Dockerfile` |

Regra geral: `<x>` → `apps/api/<x>` para tudo que era do app Rails.

## Deploy por ambiente

- **Backend:** uma imagem única, dois papéis preservados (web + worker do
  0002). `apps/api/deploy/<env>/deploy.yml` declara ambos; Kamal 2 deploya.
- **Frontends:** três deploys independentes. Cada um com seu domínio
  (`admin.rota-saude.gov.br`, `painel.<cidade>.rota-saude.gov.br`,
  `paciente.<cidade>.rota-saude.gov.br` — formato a definir). Build estático
  ou SSR conforme escolha do app (cada app decide).
- **Convenção do Kamal:** com a config em `apps/api/deploy/<env>/deploy.yml`,
  o Kamal precisa ser apontado explicitamente. **Decidido:** wrapper em
  `scripts/deploy-api.sh` que faz `kamal --config-file
  apps/api/deploy/<env>/deploy.yml deploy`. Frontends usam o pipeline do CI
  por convenção do framework escolhido.
- **Secrets por ambiente:** `deploy/<env>/secrets` carrega `RAILS_MASTER_KEY`,
  chaves do Active Record Encryption (ADR 0011), tokens do WhatsApp e
  `DATABASE_URL`. Custódia detalhada no ADR 0024.

## `scripts/` vs tarefas recorrentes

`scripts/` é **one-off operacional**, não cron. As tarefas recorrentes
(purge de `raw` 0011, purge de `domain_events` 0009, varredura de timeout
0012, reconciliação 0007) **continuam em** `apps/api/config/recurring.yml`
como Solid Queue recurring tasks. Candidatos a `scripts/`:

- `deploy-api.sh` — wrapper do Kamal com `--config-file` apropriado.
- `rebuild-projections.rb` — recompõe `dashboard_metrics` (0007).
- `replay-events.rb` — reenfileira a partir de `domain_events` (0009).
- `validate-protocol.rb` — roda JSON Schema + linter de grafo offline
  (0013/0016).
- `seed-protocol.rb` — importa/publica uma definição (0016).
- `relatorio-semanal.sh` — drift report (já existente).

## `packages/` na raiz (e não sob um app)

`ui`, `types` e `protocols` são consumidos por `api` **e** pelos três
frontends; enterrá-los sob um dos apps quebraria o compartilhamento.
`packages/protocols` guarda só o **schema/contrato neutro** da definição —
o **dado de runtime** mora no banco (0016). `packages/ui` é o que justifica
três frontends sem triplicar componente; design system compartilhado é
requisito para a separação ser sustentável.

## Consequências

- O 0002 fica desatualizado no literal; esta emenda **supersede** seus exemplos
  de caminho e dobra o número de frontends (de 1 para 3).
- **CI / Docker / Kamal** passam a ter `apps/api/` como working dir do backend;
  cada frontend ganha pipeline próprio com working dir próprio.
- Três frontends multiplicam o esforço de boilerplate inicial, mas o
  `packages/ui` mitiga duplicação real. A separação por superfície é o ganho
  arquitetural que justifica o custo.
- Documentação ganha estrutura: `docs/adr/`, `docs/modulos/`,
  `docs/operacao/`.

## Em aberto

- **Domínios dos frontends** — formato e separação de subdomínio por cidade
  (especialmente do `dashboard`).
- **Auth do `wpda`** — token assinado precisa de ADR próprio (expiração,
  revogação, rotação de chave de assinatura). Hoje é gap reconhecido.
- **`packages/types`** — segue como caveat do 0002 (fronteira Ruby ↔ TS).
- **Reconciliação de identidade do cidadão** (§2.5 da nota) — pré-condição
  para `wpda` ir além do MVP.
