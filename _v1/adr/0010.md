# ADR-0010 — Webhook do WhatsApp: ack rápido, HMAC, dedup na borda

- Status: Accepted
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0003](0003.md) (eventos), [ADR-0005](0005.md) (idempotência), [ADR-0011](0011.md) (secrets), [ADR-0014](0014.md) (HTTP fora do lock)

## Contexto

O WhatsApp Cloud API entrega eventos (mensagens recebidas, status de entrega, leituras) por webhook HTTP POST com três características operacionais que **dirigem** o design:

1. **Verificação de integridade**: cada request tem header `X-Hub-Signature-256: sha256=<hex>`, onde o hex é `HMAC-SHA256(payload_bruto, APP_SECRET)`. Sem isso, qualquer atacante na internet pode injetar mensagens falsas.
2. **Janela de ack curta**: a Meta espera `200 OK` em poucos segundos. Se demorar, **reentrega** o mesmo evento, repetidamente, e eventualmente desabilita o webhook.
3. **Verificação inicial GET**: ao registrar o webhook, a Meta faz `GET /webhooks/whatsapp?hub.mode=subscribe&hub.verify_token=...&hub.challenge=...` e espera receber `hub.challenge` cru de volta se o token bater.

Erros comuns que esse ADR existe para impedir:

- validar HMAC depois de já ter persistido (atacante grava lixo no banco mesmo com a request rejeitada);
- processar a mensagem no controller (estoura SLA, dispara reentrega, vira loop);
- não deduplicar (a mensma mensagem entra três, quatro, dez vezes durante incidentes).

## Decisão

Três camadas no caminho do webhook:

### 1. Verificação HMAC **antes de qualquer outra coisa**

`Webhooks::WhatsappController` lê o `request.raw_post`, recalcula `OpenSSL::HMAC.hexdigest("sha256", ENV["WHATSAPP_APP_SECRET"], raw)`, compara com o header usando `ActiveSupport::SecurityUtils.secure_compare`. Falha = `401`. Sem AR, sem log do payload, sem nada.

### 2. Dedup na borda via `processed_events` com `consumer = "whatsapp_webhook"`

O payload do WhatsApp traz `entry[].changes[].value.messages[].id` (id único da mensagem) e `entry[].id` (id do change). Antes de virar `DomainEvent` ou `InboundMessage`, o controller registra `(consumer: "whatsapp_webhook", event_id: <message_id>)`. Se cair na constraint única, é reentrega: responde `200 OK` direto e **não** enfileira nada.

Reutilizar a mesma tabela de [ADR-0005](0005.md) garante o mesmo invariante (exactly-once) já presente para consumidores de evento.

### 3. Persistir cru + enfileirar + ack — nessa ordem

Para cada mensagem nova:

1. `InboundMessage.create!(raw: payload, message_id: ...)` — campo `:raw` é encriptado por AR Encryption ([ADR-0011](0011.md));
2. `Events.publish("inbound_message.received", aggregate: inbound, payload: { message_id: ... })`;
3. responde `200 OK` em ~50ms.

O `ProcessInboundMessageJob` (binding em `initializers/domain_events.rb`, [ADR-0003](0003.md)) faz o parse e roda o motor de protocolos. Ele é `IdempotentConsumer` ([ADR-0005](0005.md)), então a reentrega da fila também é segura.

### Verificação GET

Quando `request.get?`, comparar `params["hub.verify_token"]` com `ENV["WHATSAPP_VERIFY_TOKEN"]` via `secure_compare`. Se bater, devolver `params["hub.challenge"]` como `text/plain`. Senão, `403`.

## Consequências

Positivas:

- atacante na internet não consegue injetar mensagem — o HMAC trava antes da primeira escrita;
- reentrega da Meta não polui banco — dedup acontece antes de qualquer `INSERT` de domínio;
- ack em ~50ms mantém a Meta feliz e a janela de reentrega vazia;
- `InboundMessage.raw` fica criptografada em repouso (LGPD) e nunca passa pelo log da aplicação;
- toda a lógica clínica acontece offline ao request (no job), portanto request-trace = só I/O.

Negativas / a vigiar:

- Postgres precisa estar disponível para o ack (precisamos do `INSERT` em `processed_events` antes do 200). Se o banco cair, devolvemos 5xx e a Meta reenfileira — comportamento aceitável e desejado;
- `secure_compare` em vez de `==` é não-negociável (timing attack na comparação do HMAC);
- log da aplicação tem que filtrar o `:raw` — adicionado em `config.filter_parameters`;
- migração futura para `WHATSAPP_APP_SECRET` rotacionado precisa suportar dois secrets simultâneos por uma janela (não implementado ainda; documentar quando precisar).

## Implementação esperada

`app/controllers/webhooks/whatsapp_controller.rb`:

- `protect_from_forgery with: :null_session` (já é API-only, não muda nada, mas explícito);
- `skip_before_action :verify_authenticity_token` (idem);
- `before_action :verify_signature!`, exceto na verificação GET;
- método `create` faz dedup + persist + publish + render `head :ok`;
- método `verify` (GET) responde ao challenge.

`app/services/whatsapp/ingest.rb` recebe o payload bruto já validado e devolve uma lista de `{ message_id:, from:, kind:, payload: }`, sem tocar AR — função pura sobre Hash.

## Alternativas consideradas

- **Validar HMAC após persistir** — derrota o objetivo; descartado;
- **Dedup no job consumidor apenas** — funciona, mas significa que toda reentrega passa por banco e fila desnecessariamente. Dedup na borda corta o custo no ponto certo;
- **Skipar 200 OK quando dedupado para forçar Meta a parar** — viola contrato Meta; ela espera 2xx para confirmar recebimento.

## Revisão

Reavaliar se:

- a janela de reentrega da Meta mudar (hoje ~5s);
- precisarmos rotacionar `APP_SECRET` ativamente (implementar suporte a dois secrets);
- a borda crescer para outros canais (SMS, Telegram) — extrair `Webhooks::SignatureVerification` como concern.
