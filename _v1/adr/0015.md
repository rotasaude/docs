# ADR-0015 — `Outcome`: tier, priority, trail

- Status: Accepted (reconstruído por referência — não havia ADR explícito original)
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0013](0013.md) (motor puro), [ADR-0017](0017.md) (scoring), [ADR-0007](0007.md) (relatórios)

## Nota

Este ADR foi reconstruído a partir de referências espalhadas no mapa de arquivos (`outcome.rb`, "tier / priority / trail") e em ADRs adjacentes. Não existia documento próprio. Tratamos como decisão tácita já em vigor — este ADR formaliza o contrato.

## Contexto

O motor de protocolos ([ADR-0013](0013.md)) precisa devolver **algo** ao chamador. Dois requisitos colidem:

1. o motor é função pura — não publica eventos, não persiste, não loga;
2. o chamador (controller, `CompleteTriagem`, frontend preview) precisa saber:
   - **terminou** ou ainda **espera resposta**?
   - se terminou, qual o **tier** clínico e **priority** de atendimento?
   - qual o **trail** percorrido (auditoria, relatório)?

Sem um objeto explícito de saída, cada caller acaba inventando o seu (`Hash`, `OpenStruct`, tupla), com nomes diferentes para a mesma coisa.

## Decisão

`Protocols::Outcome` é um Value Object imutável com três estados e quatro campos:

| campo      | tipo            | semântica                                                            |
|------------|-----------------|----------------------------------------------------------------------|
| `status`   | `:pending` ou `:terminal` | terminou o fluxo?                                          |
| `tier`     | String / nil    | rótulo clínico (`baixa`, `media`, `alta`, `indefinido`); nil se pendente |
| `priority` | Integer / nil   | ordem de atendimento dentro do tier; nil se pendente                 |
| `trail`    | Array<Hash>     | `[{ step: :idade, answer: 67, weight: 2 }, ...]` — ordem do percurso |
| `awaiting` | Symbol / nil    | id do próximo step esperando resposta; preenchido só se `:pending`    |

Construtores únicos:

```ruby
Outcome.pending(trail:, awaiting:)
Outcome.terminal(trail:, tier: nil, priority: nil, score: nil)
```

Regras:

- imutável (`freeze`);
- nada de comportamento de negócio na classe — é dado;
- serializável: `to_h` produz Hash JSON-safe, usado pelo `report_snapshot` ([ADR-0007](0007.md)) para congelar o desfecho da triagem.

## Consequências

Positivas:

- contrato único e versionável — qualquer caller (controller, job, preview) sabe o que receber;
- snapshot histórico (`ReportSnapshot`) congela o `Outcome.to_h` e a referência da definição usada — re-execução produz o mesmo desfecho;
- testes do motor verificam `Outcome` diretamente, sem mocks.

Negativas / a vigiar:

- `trail` cresce com a quantidade de steps respondidos. Não é problema para protocolos da ordem de 20 passos, mas se alguém autorizar 500-step protocols precisamos rever;
- `tier` ser String (não enum) é deliberado — cada protocolo define seu universo. Custo: typos não pegam em tempo de compilação. Mitigado pelo lint do [ADR-0016](0016.md);
- `score` em `Outcome.terminal` é opcional e específico de weighted; manter como campo livre evita explosão de subclasses.

## Convenção

Caller que recebe `Outcome` faz:

```ruby
outcome = protocol.evaluate(answers)
case outcome.status
when :pending  then ... # mostra outcome.awaiting
when :terminal then ... # despacha pelo outcome.tier
end
```

Nunca inspecionar `tier` sem checar `status` primeiro.

## Alternativas consideradas

- **Hash livre** (`{ tier:, priority:, trail: }`) — propenso a divergência entre callers;
- **Struct** — funciona mas não documenta os dois estados (pending vs terminal);
- **Subclasses (`PendingOutcome` < `Outcome`, `TerminalOutcome` < `Outcome`)** — pesado para o ganho. Adiar até precisarmos de polimorfismo real.

## Revisão

Reavaliar se:

- precisarmos representar mais estados (ex.: `:aborted` por consentimento revogado);
- `trail` virar gargalo de serialização em relatórios;
- algum protocolo precisar de múltiplos desfechos simultâneos (encaminhamento + alerta) — aí `Outcome` vira coleção.
