# ADR-0011 — Gestão de secrets e criptografia em repouso

- Status: Accepted
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0002](0002.md) (deploy Kamal), [ADR-0010](0010.md) (HMAC do WhatsApp), [ADR-0012](0012.md) (consentimento)

## Contexto

O sistema lida com dados sensíveis de saúde:

- mensagens brutas do WhatsApp (texto livre do cidadão, podendo conter sintomas, identificação, localização);
- tokens de acesso ao WhatsApp Cloud API e ao verificador de webhook;
- chaves de assinatura de relatórios públicos (`GET /r/:token`);
- credenciais de banco e do registry.

Constraints:

- não rodamos KMS gerenciado (Hostinger VPS, sem AWS/GCP KMS);
- precisamos rotacionar chaves sem reescrever o banco inteiro;
- secrets em produção não podem cair no repositório git, nem no log de deploy;
- LGPD: dados pessoais e de saúde criptografados em repouso, com purga após retenção definida.

## Decisão

Três camadas, com responsabilidades separadas:

### 1. Secrets de runtime — Kamal 2

Os valores são lidos de `apps/api/deploy/<env>/secrets`, que é interpretado pelo Kamal como shell script de exportação. Esse arquivo:

- **não** contém o valor em texto plano;
- **chama** uma fonte externa (`1password read`, `aws ssm get-parameter`, `op://...`, `pass`, `gh secret list`, etc.);
- é versionado no git (só referências, sem segredo).

Em desenvolvimento, é aceitável ler de `.env.development.local` ignorado pelo git; em produção, exige cofre externo (1Password CLI é o padrão inicial do time).

### 2. Master key do Rails

`config/master.key` **nunca** é commitada. É distribuída via `RAILS_MASTER_KEY` no secrets do Kamal. Ela descriptografa `config/credentials.yml.enc`, que guarda apenas o que precisa ficar versionado (ex.: chaves públicas, IDs de templates do WhatsApp).

Valores que **não** entram em credentials.yml.enc por serem realmente sensíveis ou rotacionáveis com frequência:

- `WHATSAPP_ACCESS_TOKEN` (rotaciona; vem do cofre);
- `WHATSAPP_APP_SECRET` (usado no HMAC do webhook — ADR-0010);
- `DATABASE_URL` (composta a partir do cofre);
- `REPORT_SIGNING_KEY` (assina tokens de `/r/:token`).

### 3. Active Record Encryption para dados sensíveis em repouso

Usamos `ActiveRecord::Encryption` (built-in Rails) com duas chaves rotacionáveis (`primary_key`, `deterministic_key`) + um salt. Aplicado em:

- `InboundMessage#raw` — payload bruto do WhatsApp Cloud API;
- `Conversation` — campos com identificadores diretos do cidadão;
- `Consent` — provas de consentimento.

As chaves vêm de credentials criptografadas (`active_record_encryption.primary_key`, `…deterministic_key`, `…key_derivation_salt`), portanto a posse da `RAILS_MASTER_KEY` é suficiente para ler o banco — e a perda dela é o pior incidente operacional possível.

## Consequências

Positivas:

- nenhum segredo no git, mesmo com o secrets-file versionado;
- master key única por ambiente como pivot — fácil de auditar quem tem acesso;
- AR Encryption funciona transparente para a aplicação; queries em campos determinísticos seguem funcionando;
- purga de dados sensíveis pode ser feita por `UPDATE … SET raw = NULL` após retenção, sem precisar girar chave (ver `config/recurring.yml`, ADR-0007 mencionará).

Negativas / a vigiar:

- master key perdida = todos os dados criptografados ficam inacessíveis. Backup da master key fora do servidor é mandatório (cofre pessoal + cópia offline);
- AR Encryption tem overhead em índices: campos `:raw` só podem ser pesquisados se forem determinísticos; deixamos `:raw` como não-determinístico e indexamos campos derivados;
- rotação de chave exige `bin/rails db:encryption:rotate` controlado e janela de manutenção;
- secrets-file via 1Password CLI exige `op` instalado no host de deploy — virou pré-requisito do runbook.

## Alternativas consideradas

- **dotenv direto no servidor** — secrets ficam em disco no host, qualquer SSH = leak; descartado;
- **Vault / Infisical self-hosted** — overhead operacional alto para o tamanho atual; reavaliar quando passarmos de 3 municípios;
- **AR Encryption com chave por tenant (município)** — proteção a mais, mas multiplica complexidade de rotação. Postergado.

## Procedimento operacional

1. Gerar chaves AR Encryption uma vez: `bin/rails db:encryption:init`.
2. Guardar saída em `EDITOR=vim bin/rails credentials:edit --environment <env>`.
3. `RAILS_MASTER_KEY` (config/credentials/<env>.key) vai para o cofre, **nunca** para o git.
4. `apps/api/deploy/<env>/secrets` lê do cofre e exporta as variáveis listadas em `env.secret` do `deploy.yml`.

## Revisão

Reavaliar se:

- formos obrigados a separar chave por município (multi-tenant forte);
- precisarmos atender exigência de KMS gerenciado por contrato municipal;
- o time crescer a ponto de o 1Password CLI virar gargalo operacional.
