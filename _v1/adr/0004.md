# ADR-0004 — `enqueue_after_transaction_commit` por padrão

- Status: Accepted
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0001](0001.md) (Solid Queue), [ADR-0003](0003.md) (domain events), [ADR-0005](0005.md) (idempotência), [ADR-0009](0009.md) (audit + reenfileiramento)

## Contexto

Comandos do domínio (`CompleteTriagem`, `GiveConsent`, `IngestInboundMessage`, ...) abrem transação no Postgres e, no caminho feliz, disparam jobs:

- `ProcessInboundMessageJob`
- `SendWhatsappJob` (HTTP fora do lock — ADR-0014)
- `GenerateReportJob`, `UpdateDashboardJob`
- `NotifyCitizenJob`, `AlertMunicipalityJob`

Comportamento padrão histórico do Active Job: `perform_later` enfileira **imediatamente**, antes do `COMMIT`. Isso produz duas patologias clássicas:

1. **Job vê estado que não existe**: roda antes do commit e `Record.find(id)` levanta `RecordNotFound`, ou pior, lê uma versão antiga via réplica;
2. **Job roda apesar do rollback**: a transação dá rollback (validação, deadlock, exception subsequente) mas o WhatsApp já foi disparado, o cidadão recebeu mensagem de algo que não aconteceu.

Solid Queue ([ADR-0001](0001.md)) é Postgres-backed, então temos a opção de enfileirar **dentro** da mesma transação e deixar o COMMIT decidir.

## Decisão

Habilitar `config.active_job.enqueue_after_transaction_commit = :always` em `config/application.rb`. Todo `perform_later` que ocorrer dentro de uma transação espera o COMMIT; se houver ROLLBACK, o job nunca é enfileirado.

Exceções permitidas (mantidas como código explícito, não como default):

- envio de job que não toca estado de domínio e é seguro mesmo com rollback (ex.: métrica de telemetria pura). Nesses casos, documentar no call-site.

## Consequências

Positivas:

- comportamento consistente em todos os comandos: ou a transação commitou e o efeito externo dispara, ou nada acontece;
- elimina toda uma classe de bugs de "job não encontra o registro";
- combina bem com a tabela `processed_events` ([ADR-0005](0005.md)): commit grava o evento e enfileira o consumidor no mesmo átomo lógico;
- simplifica o raciocínio sobre saga / outbox — não precisamos implementar outbox manual nessa fase do projeto.

Negativas / a vigiar:

- latência: o job só fica visível ao worker depois do COMMIT. Em transações longas isso atrasa o trabalho de fundo. Mitigado mantendo transações curtas;
- se houver `after_commit do enqueue_x end` espalhado por callbacks, vira redundante / confuso — preferir enfileirar no Command Object, não em callback do AR;
- testes que esperam "enfileirado antes" precisam usar `assert_enqueued_with` dentro de bloco `perform_enqueued_jobs` ou explicitamente commitar fixtures.

## Alternativas consideradas

- **Outbox pattern manual** (gravar linha em `outbox_events` e ter relay) — mais robusto a longo prazo, mas Solid Queue + `enqueue_after_transaction_commit` cobre 95% dos casos com 5% do custo. Adiar até precisar replicar para fora do Postgres;
- **Default `:never`** com cada call-site escolhendo — propenso a esquecimento e divergência entre desenvolvedores;
- **Default `:always` apenas em produção** — incoerência entre ambientes mascara bugs em dev.

## Revisão

Reavaliar se:

- precisarmos publicar eventos para fora do Postgres (Kafka, fila externa) — aí o outbox passa a valer o custo;
- transações de domínio crescerem a ponto de a latência adicional virar problema operacional.
