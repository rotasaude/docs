# ADR-0017 — Scoring com duas estratégias: weighted e decision_table

- Status: Accepted
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0013](0013.md) (motor puro), [ADR-0015](0015.md) (Outcome), [ADR-0016](0016.md) (storage)

## Contexto

Uma definição de protocolo precisa, ao final do fluxo, produzir um `Outcome` ([ADR-0015](0015.md)) com `tier`, `priority` e `trail`. Como exatamente?

Os protocolos clínicos em uso real seguem dois grandes estilos:

1. **Pontuação acumulada** — cada resposta tem peso; soma cruzando faixas (ex.: 0-3 baixa, 4-7 média, 8+ alta). Comum em escalas de risco respiratório, escalas de dor;
2. **Tabela de decisão** — combinações específicas de respostas mapeiam direto para um tier (ex.: "se febre AND falta-de-ar então urgência"). Comum em fluxos onde o sintoma marcador domina.

Forçar tudo em uma estratégia única leva a:

- weighted-only: tabelas viram um monte de pesos absurdos (10000, 99999) para forçar combinação determinística;
- decision-table-only: pontuação contínua vira combinatória de linhas; mantenção vira pesadelo.

A equipe clínica precisa autorar nos dois estilos. Logo, o motor precisa **declarar** que escolheu uma estratégia, e o storage precisa permitir essa escolha por protocolo.

## Decisão

Duas estratégias de scoring como classes em `app/protocols/scoring/`, escolhidas via campo `scoring.type` na definição:

```yaml
scoring:
  type: weighted
  thresholds:
    baixa: 0
    media: 4
    alta: 8
```

ou

```yaml
scoring:
  type: decision_table
  rules:
    - when: { febre: "sim", falta_ar: "sim" }
      tier: alta
      priority: 1
    - when: { febre: "sim" }
      tier: media
      priority: 5
    - else: { tier: baixa, priority: 9 }
```

Cada estratégia implementa a mesma interface mínima:

```ruby
class Scoring::Weighted
  def call(trail)  -> Outcome
  def to_h         -> Hash  # round-trip serializável
end
```

`Protocol#evaluate` ([ADR-0013](0013.md)) delega ao scoring no fim do trail; sem scoring, devolve `Outcome.terminal(trail:)` sem tier.

`Scoring.build(hash)` é a fábrica que escolhe a classe pelo `type` — análoga a `Definitions.build`.

### Trail = entrada canônica

Ambas as estratégias recebem o **trail completo** (lista de `{ step:, answer: }`), não as respostas brutas. Isso permite:

- weighted somar `step.weights[answer]` linearmente;
- decision_table conferir matchers contra o trail;
- futuras estratégias (ex.: machine learning, rule engine externo) terem acesso ao mesmo formato.

### tier e priority

`tier` (string) é o rótulo clínico (`baixa`, `media`, `alta`). `priority` (inteiro) é a ordem de atendimento dentro do tier. Detalhes vivem em [ADR-0015](0015.md); aqui só importa que ambas as estratégias produzem os dois.

## Consequências

Positivas:

- equipe clínica tem dois idiomas naturais para autorar, mais legíveis e auditáveis que um único genérico;
- adicionar uma terceira estratégia é uma classe nova em `scoring/` + dispatch em `Scoring.build` — zero alteração no motor;
- testar scoring fica trivial: classe pura, função pura.

Negativas / a vigiar:

- duas implementações para manter em paralelo (Ruby + TS no preview, mesma duplicação do [ADR-0013](0013.md)). Mitigamos com o JSON Schema único de scoring em `packages/protocols/`;
- mistura num mesmo protocolo (ex.: "weighted exceto se febre = sim aí pula para alta") não cabe. Isso seria uma terceira estratégia — não fingir que cabe;
- thresholds e rules precisam ser **estáveis sob ordenação**: weighted é trivial; decision_table tem que ser ordenada e a primeira regra que casa ganha. Documentar e testar.

## Estrutura

```
app/protocols/scoring/
├── weighted.rb         # soma trail × pesos, casa thresholds
└── decision_table.rb   # primeira regra que casa ganha; else é fallback
```

`Protocol#evaluate` passa o trail; quem produz o `Outcome` é a classe escolhida.

## Alternativas consideradas

- **Linguagem de regra única** (JSON Logic, CEL) — expressivo, mas difícil de revisar por equipe clínica e duplica esforço com o frontend;
- **Strategy via Ruby (`scoring: lambda { |trail| … }`)** — viola pureza/serialização do [ADR-0013](0013.md);
- **Scoring fora do motor** (job dedicado) — quebra o invariante "`evaluate` é função pura do trail".

## Revisão

Reavaliar se:

- aparecer protocolo que precise mesclar as duas estratégias dentro do mesmo fluxo;
- precisarmos calibrar pesos via dados (ML) — então scoring vira parametrizado por modelo treinado;
- decision_table crescer a ponto de a primeira-regra-ganha virar fonte de bug — então passamos a exigir não-sobreposição via lint.
