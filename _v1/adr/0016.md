# ADR-0016 — Storage de definições no Postgres, façade `Protocols.current`, UI de autoria

- Status: Accepted (parcial — UI de autoria em aberto)
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0013](0013.md) (motor puro), [ADR-0015](0015.md) (Outcome), [ADR-0017](0017.md) (scoring)

## Contexto

O motor de [ADR-0013](0013.md) é puro: recebe um Hash, devolve um `Protocol`. Mas precisa vir de algum lugar:

- **YAML em disco** — bom para POC, péssimo para autoria por equipe clínica e para multi-tenant (cada município pode customizar);
- **Tabela no Postgres** — definições viram dado de aplicação, versionáveis, audíveis, autoríveis pela UI;
- **Repositório git separado para definições** — bom para governance, ruim para latência de mudança e para audit linkado à triagem que usou a versão.

Casos de uso reais:

1. **Triagem em produção** precisa carregar **a** definição ativa para um par `(municipality, protocol_name)` com latência sub-segundo;
2. **Relatório histórico** ([ADR-0007](0007.md)) precisa carregar **a** definição usada por uma triagem específica, mesmo que ela já tenha sido aposentada;
3. **UI de autoria** precisa permitir criar nova versão sem afetar a versão ativa;
4. **Lint offline** ([ADR-0013](0013.md)) precisa rodar contra um JSON Schema único, compartilhado com o frontend.

## Decisão

Três peças:

### 1. Tabela `protocol_definitions`

| coluna           | tipo         | nota                                                |
|------------------|--------------|-----------------------------------------------------|
| `id`             | uuid         |                                                     |
| `name`           | string       | `triagem-respiratoria`, `triagem-cardio`...         |
| `version`        | integer      | monotônico por `name`                               |
| `municipality_id`| uuid null    | null = definição global; preenchido = override      |
| `definition`     | jsonb        | a definição em si (validada via JSON Schema)        |
| `status`         | enum         | `draft`, `active`, `retired`                        |
| `activated_at`   | timestamptz  |                                                     |
| `retired_at`     | timestamptz  |                                                     |

Índices:

- único parcial `(name, municipality_id) WHERE status = 'active'` — só uma versão ativa por par;
- `(name, version, municipality_id)` para lookup direto.

`Definition` é apenas armazenamento — toda a lógica vive em `Protocols::Protocol` (ADR-0013).

### 2. Façade `Protocols.current` / `Protocols.fetch`

Vive em `app/protocols/protocols.rb`. É o **único lugar** do projeto que junta o motor puro com o banco. O resto do app sempre passa por essa façade:

```ruby
protocol = Protocols.current(name: "triagem-respiratoria", municipality: m)
outcome = protocol.evaluate(answers)

# Para relatórios históricos, busca pela versão exata:
protocol = Protocols.fetch(name: "triagem-respiratoria", version: 7, municipality_id: m_id)
```

A façade resolve precedência: definição com `municipality_id` específico ganha de definição global; entre essas, `status = active`.

A façade **carrega cacheado**. Cache key inclui `(name, version, municipality_id)`. A invalidação acontece em `after_commit` da `Definition` quando muda de status (ver [ADR-0007](0007.md) para implicações em snapshots).

### 3. JSON Schema único em `packages/protocols/`

`packages/protocols/schema.json` é o contrato. Tanto o motor Ruby (`Validator`, ADR-0013) quanto o preview TS no frontend ([ADR-0013](0013.md) menciona a duplicação) consomem o mesmo schema. Definições que não passam pelo schema **não entram no banco** — bloqueio acontece em `Definition#before_save`.

## Consequências

Positivas:

- definições viram dado de aplicação, com histórico, audit e diff;
- relatório histórico fica trivial — o `report_snapshot` ([ADR-0007](0007.md)) guarda o `definition_id` exato usado;
- multi-tenant ganha override por município sem fork de código;
- frontend e backend compartilham o mesmo contrato — schema é a fonte da verdade.

Negativas / a vigiar:

- mudança em schema é breaking change para definições existentes; precisa de migração versionada por `definition.schema_version`;
- cache exige invalidação consistente — qualquer mutação direta no banco (via psql) deixa app inconsistente até reboot;
- a façade vira ponto de coordenação: testes do motor não devem tocar a façade.

## UI de autoria — em aberto

A UI fica em `apps/web/src/protocols/`. Decisões deliberadamente adiadas:

- formato de edição (form-tree vs JSON editor vs visual);
- fluxo de revisão (peer review necessário antes de ativar?);
- preview side-by-side com versão ativa.

Por enquanto, autoria acontece via `scripts/import_protocol_definition.rb`: lê YAML do disco, valida, cria `Definition` em status `draft`. A ativação é feita por `bin/rails runner` operacional.

Este ADR será atualizado quando a UI for definida.

## Scripts associados

- `scripts/import_protocol_definition.rb` — importa/publica uma definição;
- `scripts/validate_protocol_definition.rb` — roda `Validator` offline (sem banco, sem Rails — chama o motor diretamente).

## Alternativas consideradas

- **YAML em `config/protocols/*.yml`** — sem multi-tenant, sem audit, sem snapshot histórico real;
- **Definição em repositório git separado** — boa governance, mas latência de mudança alta e linkagem audit complexa;
- **Definição inline no código** ([ADR-0013](0013.md) descartou).

## Revisão

Reavaliar se:

- precisarmos de assinatura criptográfica de definições (governance forte);
- a UI de autoria mostrar que `municipality_id` insuficiente para o modelo de tenancy real;
- cache do Rails virar ponto de inconsistência em produção.
