# ADR-0006 — Commands com `Result`: ações de domínio explícitas e composáveis

- Status: Accepted
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0003](0003.md) (eventos), [ADR-0004](0004.md) (commit-then-enqueue), [ADR-0013](0013.md) (motor), [ADR-0017](0017.md) (Outcome)

## Contexto

Toda mudança de estado relevante do rota-saúde tem formato comum:

1. ler estado (triagem, conversa, consentimento);
2. rodar uma regra de domínio (motor de protocolos, máquina de estados, validação);
3. persistir mudanças;
4. publicar evento(s).

Patrões alternativos:

- **Tudo no controller** — vira controller gigante, impossível reusar entre webhook e UI, impossível testar sem `request spec`;
- **Tudo no model (callback)** — esconde regras críticas dentro de `after_save`, difícil de auditar, fácil de cair em recursão;
- **Service objects soltos** — funciona mas convive com inconsistências: cada um define erro de jeito diferente (`raise`, `return false`, `Result`, `nil`);
- **Resque/Sidekiq jobs como comando** — confunde "decisão" com "efeito" e mistura com [ADR-0014](0014.md).

O caso central é `CompleteTriagem`: tem dois callers (job que consome inbound, UI futura), três modos de falha (sem consentimento, triagem inexistente, protocolo inválido), e precisa publicar dois eventos diferentes (`triagem.completed` no caminho feliz, `triagem.urgent` quando o tier exigir alerta).

## Decisão

Padrão de Command Object com `Result` como valor de retorno único. Estrutura:

### `app/commands/result.rb`

Value Object imutável com dois construtores:

```ruby
Result.ok(payload)
Result.fail(:reason, message: "...", details: {})
```

E uma API mínima: `ok?`, `failure?`, `reason`, `message`, `payload`, `to_h`. Comandos nunca devolvem `nil`, nunca devolvem AR direto, nunca usam `raise` para falha esperada.

### Convenção de Commands

Cada comando é uma classe em `app/commands/` com `.call(**kwargs) -> Result` como ponto único de entrada:

```ruby
class CompleteTriagem
  def self.call(triagem:, answer:) = new(triagem: triagem, answer: answer).call

  def call
    return Result.fail(:no_consent)         unless conversation.consented?
    return Result.fail(:already_completed)  if triagem.completed?

    triagem.with_lock do
      outcome = protocol.evaluate(triagem.answers.merge(triagem.current_step => answer))
      return Result.fail(:invalid_answer)   if outcome.terminal? && outcome.tier.nil?

      triagem.append_answer!(answer)
      triagem.complete!(outcome) if outcome.terminal?

      Events.publish("triagem.completed", aggregate: triagem, payload: outcome.to_h) if outcome.terminal?
      Events.publish("triagem.urgent",    aggregate: triagem, payload: outcome.to_h) if outcome.terminal? && outcome.tier == "alta"
    end

    Result.ok(triagem: triagem, outcome: outcome)
  end
end
```

Regras invioláveis:

- comando **não** chama HTTP — quem chama é job ([ADR-0014](0014.md));
- comando **roda em transação** (explícita ou herdada) — eventos via `Events.publish` participam dela;
- comando **devolve Result**, sempre;
- comando **não conhece controller, request, params** — recebe objetos de domínio.

### Mapeamento Result → resposta

Controller traduz `Result` em HTTP; job traduz `Result` em log + retry. Tradução fica fora do comando:

```ruby
case CompleteTriagem.call(triagem: t, answer: a)
in Result(ok?: true, payload:)             then render json: payload
in Result(failure?: true, reason: :no_consent) then head :forbidden
in Result(failure?: true)                  then head :unprocessable_entity
end
```

## Consequências

Positivas:

- contratos previsíveis: lendo o nome do comando você sabe entradas e saídas;
- composição: um comando pode chamar outro e propagar `Result`;
- testabilidade: comando puro em RSpec, sem controller, sem job, sem HTTP;
- audit linkado: comando publica evento → tabela `domain_events` é a história ([ADR-0003](0003.md));
- erros esperados ficam visíveis como `Result.fail(:reason)`, não como `rescue StandardError`.

Negativas / a vigiar:

- ainda mais classes — o time precisa aceitar 4 commands para "uma feature" sem reclamar;
- não esquecer que comando publica evento **antes** do COMMIT, mas o consumidor só roda depois ([ADR-0004](0004.md)) — confundir os dois é fonte clássica de bug;
- `Result.fail(:reason)` exige `reason` em snake_case curto, codificado por enum implícito. Documentar `reasons` por comando na própria classe.

## Estrutura inicial em `app/commands/`

| Command            | Entradas                          | Eventos publicados                |
|--------------------|-----------------------------------|-----------------------------------|
| `CompleteTriagem`  | `triagem:, answer:`               | `triagem.completed`, `triagem.urgent` |
| `GiveConsent`      | `conversation:, version:`         | `consent.given`                   |
| `RevokeConsent`    | `conversation:`                   | `consent.revoked`                 |

`IngestInboundMessage` **não** é command (o webhook ([ADR-0010](0010.md)) faz o `INSERT` direto e publica `inbound_message.received`). Justificativa: o webhook tem que ser rápido e não tem decisão de domínio — só registra fato.

## Alternativas consideradas

- **Sem padrão (ad-hoc)** — testado em outros projetos do time, gera proliferação de jeitos diferentes de devolver falha;
- **Padrão de Interactor (gem `interactor`)** — equivalente em essência, adiciona gem por nada;
- **Operation/Transaction (Trailblazer)** — overhead alto, opinião arquitetural forte demais para o tamanho do time.

## Revisão

Reavaliar se:

- a quantidade de commands explodir (>30) sem agrupamento natural — então introduzir `app/commands/<contexto>/` por bounded context;
- precisarmos de hooks transversais (instrumentação, autorização) — então transformar `Command` em superclasse com `around_call`.
