# ADR-0014 — HTTP fora do lock: separar trabalho transacional do envio externo

- Status: Accepted
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0005](0005.md) (idempotência), [ADR-0008](0008.md) (filas), [ADR-0010](0010.md) (webhook), [ADR-0004](0004.md) (commit-then-enqueue)

## Contexto

Consumidores idempotentes ([ADR-0005](0005.md)) rodam o corpo dentro de uma transação Postgres aberta — é o que dá a garantia exactly-once. Mas chamadas HTTP externas (WhatsApp Cloud API, notificação a sistemas de prefeitura, webhooks de saída) têm três propriedades incompatíveis com viver dentro de transação:

1. **Latência variável**: Cloud API pode responder em 80ms ou em 4s; segurar conexão Postgres por isso é desperdício e amplifica contenção;
2. **Falha não-transacional**: o envio pode ter sido aceito pela Meta enquanto o lado Rails recebe timeout — `rescue` + retry chama de novo, duplica;
3. **Latência amplifica deadlock**: transação longa = janela de deadlock maior; HTTP dentro dela transforma incidente local em pico de retries.

Erros comuns que esse ADR existe para impedir:

- chamar `cloud_api.send_message` de dentro do `consume(event)`;
- segurar `Triagem#with_lock` por todo o tempo de uma resposta HTTP;
- usar `after_commit` para disparar HTTP — funciona, mas espalha a regra por callbacks e mistura com idempotência.

## Decisão

Todo efeito colateral fora do banco (HTTP, e-mail, push, fila externa) **mora em job próprio**, separado do consumidor que toma a decisão de domínio.

Regra operacional:

1. **Consumidor idempotente** ([ADR-0005](0005.md)) faz só trabalho transacional: lê estado, valida invariantes, escreve mudanças, publica eventos novos;
2. **Antes de commitar**, enfileira o job de envio com os dados literais necessários (`to`, `template`, `context`), via `perform_later` — graças a [ADR-0004](0004.md), só vira fila visível depois do COMMIT;
3. **Job de envio** (ex.: `SendWhatsappJob`) abre **sem** transação, chama HTTP, trata retry. Não toca AR fora de gravar status (em transação curta separada).

`SendWhatsappJob` mora na fila `realtime` ([ADR-0008](0008.md)) e:

- recebe **dados literais**, não ids — payload do job é a fonte da verdade do envio;
- usa idempotency key própria (`message_id + to` ou um uuid gerado pelo caller) passada ao Cloud API via `messaging_product` + `recipient_type` + `to`;
- `retry_on Net::HTTPError, attempts: 5, wait: :polynomially_longer`;
- registra `OutboundMessage.create!(status:, response:)` em transação curta separada após retorno da Cloud API.

## Consequências

Positivas:

- transação do consumidor fica curta (milissegundos), liberando conexão Postgres rapidamente;
- falha de HTTP não rebobina a decisão de domínio — a mudança de estado já está commitada;
- retry de HTTP é local ao job de envio, com política própria;
- visibilidade: profundidade da fila `realtime` reflete pressão HTTP, não trabalho de domínio.

Negativas / a vigiar:

- janela entre COMMIT do domínio e envio efetivo: estado existe sem mensagem despachada. Aceitável e visível via `OutboundMessage.pending`;
- duplicata possível se o job de envio for retentado depois de a Cloud API ter aceito mas o Rails ter atingido timeout. Mitigamos com **idempotency key** na request à Meta (o que a Cloud API suporta);
- payload do job carrega dados que podem ficar "obsoletos" entre o enfileiramento e a execução (rara). Aceitar: a fila é a fonte da verdade do que vai ser enviado naquele momento.

## Padrão de uso

```ruby
class ProcessInboundMessageJob < ApplicationJob
  include IdempotentConsumer
  queue_as :realtime

  def consume(event)
    # trabalho transacional — só banco
    triagem.record_answer!(answer)

    # HTTP delegado — passa dados literais
    SendWhatsappJob.perform_later(
      to: inbound.from,
      template: triagem.next_prompt_template(outcome),
      context: { triagem_id: triagem.id }
    )
  end
end
```

```ruby
class SendWhatsappJob < ApplicationJob
  queue_as :realtime
  retry_on Net::HTTPError, attempts: 5, wait: :polynomially_longer

  def perform(to:, template:, context: {})
    # SEM transação aberta — só HTTP.
    result = Whatsapp::Outbound.deliver_template(to: to, template: template, idempotency_key: digest(to, template, context))
    OutboundMessage.create!(to: to, template: template, status: result.status, response: result.body)
  end
end
```

`SendWhatsappJob` **não** inclui `IdempotentConsumer` — não é consumidor de evento, é enfileirado direto. A garantia de não-duplicação vem da idempotency key passada à Cloud API.

## Alternativas consideradas

- **HTTP no consumidor com timeout agressivo** — não resolve duplicata e mantém transação longa;
- **after_commit callback no AR** — espalha regra, dificulta replay e teste;
- **Outbox externo com relay process** — sobreentendido como certo no longo prazo; adiar enquanto Solid Queue resolve.

## Revisão

Reavaliar se:

- o número de canais externos crescer (Telegram, SMS, e-mail) — extrair `Outbound::Channel` abstrato;
- a Cloud API mudar suporte a idempotency key;
- precisarmos garantir ordenação rigorosa de mensagens dentro de uma conversa (hoje confiamos no ack do consumidor).
