# ADR-0013 — Motor de protocolos como módulo puro

- Status: Accepted
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0015](0015.md) (Outcome), [ADR-0016](0016.md) (storage + UI), [ADR-0017](0017.md) (scoring)

## Contexto

O coração funcional do rota-saúde é o **protocolo de triagem**: uma sequência de perguntas, validações e decisões que, dado um conjunto de respostas, produz um desfecho (encaminhamento, tier de urgência, instruções ao cidadão). Os protocolos não são código: são dados, autorados por equipes clínicas, versionados, auditáveis.

Existem três modos errados de organizar isso:

1. **Hardcodar cada protocolo como Ruby** — bom para uma versão, péssimo para evolução; cada protocolo novo é deploy;
2. **DSL de protocolo dentro do Rails app** — funciona, mas mistura código clínico com infra (banco, jobs, controllers), torna teste lento e dificulta uso fora do Rails (preview no frontend, lint offline);
3. **Engine externo (regra de negócio fora do repositório)** — desproporcional para hoje, e desalinhado com o time atual ter Ruby como linguagem principal.

Restrições reais:

- a equipe clínica precisa **revisar** definições sem rodar Rails;
- o frontend precisa **simular** o protocolo (preview de autoria, [ADR-0016](0016.md)) com a mesma lógica que produção;
- precisamos **validar offline** uma definição antes de subir ao banco (`scripts/validate_protocol_definition.rb`).

## Decisão

Implementar o motor como um **módulo Ruby puro** sob `app/protocols/`, sem dependências de Active Record, Active Job ou controllers. Componentes:

- `Protocol` — agregado raiz: nome, versão, lista de `Step`s, configuração de scoring;
- `Step` — uma pergunta + validações + ramificação;
- `Validator` — aplica um JSON Schema sobre a definição e gera erros legíveis;
- `Definitions` — fábrica: recebe um Hash (vindo de YAML/JSON/banco) e devolve um `Protocol` instanciado.

Regras invioláveis do módulo:

1. **não importa Rails**;
2. **não toca banco** (a leitura do storage acontece em `Protocols.fetch`, ver [ADR-0016](0016.md), que está **fora** do motor);
3. **não tem efeito colateral** — todo método é função pura sobre os argumentos;
4. **é totalmente serializável**: um `Protocol` instanciado pode ser dumpado de volta para o Hash original sem perda;
5. **erra cedo**: definição inválida = exceção na construção, nunca em runtime.

`Protocol#step(answers)` devolve o próximo `Step` dado um conjunto de respostas; `Protocol#evaluate(answers)` percorre o fluxo completo e devolve um `Outcome` (ver [ADR-0015](0015.md)). As duas APIs aceitam respostas parciais e nunca levantam por dado faltante — devolvem `:pending` ou um `Outcome` parcial.

## Consequências

Positivas:

- **testabilidade**: suite roda em milissegundos, sem banco;
- **portabilidade**: o mesmo módulo é usado pelo Rails app, pelo script de validação offline e (com adaptação JS — ver [ADR-0016](0016.md)) pelo preview no frontend;
- **separação clara de responsabilidades**: o motor decide; o storage carrega; o controller orquestra;
- **revisão clínica direta**: um YAML de protocolo + `Validator` + suite de casos = ciclo completo sem Rails.

Negativas / a vigiar:

- duplicação inevitável entre motor Ruby e preview TS no frontend. Mitigamos com [ADR-0016](0016.md) (JSON Schema único + validador compartilhado em `packages/protocols/`);
- "puro" exige disciplina: nenhuma chamada de `Rails.logger`, nada de `Time.zone.now` — tempo entra por argumento, log fica para o caller;
- mudanças no motor afetam todos os protocolos vivos ao mesmo tempo. Schema versionado mitiga.

## Estrutura de arquivos

```
app/protocols/
├── protocol.rb        # agregado raiz
├── protocols.rb       # façade Protocols.current/fetch — NÃO faz parte do motor puro (ADR-0016)
├── definitions.rb     # fábrica Hash -> Protocol
├── step.rb            # passo individual
├── outcome.rb         # ADR-0015
├── validator.rb       # JSON Schema + linter
└── scoring/
    ├── weighted.rb     # ADR-0017
    └── decision_table.rb
```

`protocols.rb` mora junto por proximidade, mas a regra de pureza vale apenas dos demais arquivos (ver [ADR-0016](0016.md) para a justificativa).

## Alternativas consideradas

- **DSL Ruby (`protocol "foo" do; step :idade; end`)** — bonito, mas vincula a definição ao runtime Rails e impede o lint offline;
- **Workflow engine externo (Camunda, Temporal)** — sobrecarga operacional gigantesca para o caso;
- **JSON Logic / regras como expressão única** — não cobre estado / ramificação razoavelmente.

## Revisão

Reavaliar se:

- precisarmos rodar protocolos em runtime não-Ruby (ex.: edge function) — aí o JSON Schema vira o contrato e cada runtime tem seu próprio motor compatível;
- a definição passar a precisar de side-effects mid-flow (chamar API externa entre dois steps) — aí o motor precisa expor hooks explícitos.
