# ADR-0002 — Imagem Docker única, papéis web e worker via Kamal 2

- Status: Accepted
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0001](0001.md) (Solid Queue + `bin/jobs`), [ADR-0008](0008.md) (filas), [ADR-0011](0011.md) (secrets)

## Contexto

A API tem dois processos de runtime distintos:

- **web** — Rails server respondendo HTTP (webhook do WhatsApp, painel, `/r/:token`);
- **worker** — supervisor da Solid Queue ([ADR-0001](0001.md)) processando jobs.

Os dois processos compartilham 100% do código (modelos, jobs, services, motor de protocolos). As alternativas para empacotar e implantar são:

1. **Duas imagens distintas** — uma para web, outra para worker;
2. **Uma imagem única** com `CMD` diferente por papel;
3. **Mono-processo** rodando web e worker no mesmo container.

A operação será feita pela própria equipe, sem SRE dedicado, com Kamal 2 sobre VPS Hostinger (mesma stack que o time já opera).

## Decisão

Adotar **uma única imagem Docker** ([Dockerfile](../../apps/api/Dockerfile)), com o papel selecionado pelo `cmd` de cada role do Kamal 2:

```yaml
servers:
  web:
    hosts: [...]
    # CMD default da imagem: ./bin/rails server
  worker:
    hosts: [...]
    cmd: ./bin/jobs
```

A organização do repositório segue o monorepo:

- `apps/api/` — Rails 8, fonte única da imagem;
- `apps/api/deploy/development/`, `apps/api/deploy/production/` — um `deploy.yml` por ambiente;
- `packages/` — código compartilhado entre `apps/api` e `apps/web` (tipos, definições de protocolo). Não vai dentro da imagem da API a menos que seja necessário em runtime.

Mono-processo (opção 3) foi descartado: degrada isolamento de falha (uma OOM do worker derruba o web) e impede escalar os papéis de forma independente.

## Consequências

Positivas:

- build e cache de imagem únicos; `kamal deploy` empurra um único artefato e troca os dois papéis no mesmo release, eliminando deriva entre web e worker;
- rollback atômico: a mesma SHA está nos dois papéis;
- onboarding mais simples — quem entende o web entende o worker, é o mesmo `Gemfile.lock` e o mesmo `bundle exec`;
- Kamal 2 trata cada role como cidadão de primeira classe (deploys, healthchecks, logs separados).

Negativas / a vigiar:

- a imagem carrega dependências que só uma role usa (ex.: assets compilados para web; gems de fila para worker). Aceitável dado o tamanho atual; reavaliar se ultrapassar ~500 MB compactada;
- escalonamento de web e worker exige números iguais de réplicas por host *ou* listas de hosts separadas em `servers.web.hosts` e `servers.worker.hosts`. Resolvido por configuração, não por imagem;
- precisamos manter o `Gemfile` enxuto — qualquer dependência nova entra nos dois papéis.

## Topologia de papéis

| Papel  | CMD                          | Porta | Healthcheck       | Réplicas iniciais |
|--------|------------------------------|-------|-------------------|-------------------|
| web    | `./bin/rails server`         | 3000  | `GET /up`         | 2                 |
| worker | `./bin/jobs`                 | —     | processo vivo     | 1                 |

Ambientes:

- **development** (`apps/api/deploy/development/deploy.yml`) — host único, 1 web + 1 worker, banco compartilhado em accessory local;
- **production** (`apps/api/deploy/production/deploy.yml`) — pelo menos 2 hosts web, 1 worker; banco como accessory dedicado (ver [ADR-0011](0011.md) para secrets).

## Alternativas consideradas

- **Duas imagens** — duplica build, aumenta superfície de deriva, sem ganho real;
- **Heroku/Render-style mono-processo** — incompatível com isolamento de falha e com `bin/jobs` como supervisor independente.

## Revisão

Reavaliar se:

- a imagem ultrapassar 500 MB compactada;
- web e worker precisarem de stacks de runtime divergentes (ex.: extensão nativa só do worker);
- alguma role começar a precisar de dependências de sistema operacional não compartilháveis.
