# ADR-0003 — Eventos de domínio com tabela de auditoria e bindings declarativos

- Status: Accepted
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0004](0004.md) (enqueue_after_transaction_commit), [ADR-0005](0005.md) (idempotência), [ADR-0009](0009.md) (audit + reenfileiramento)

## Contexto

A regra de orquestração do rota-saúde é:

> Comandos mudam estado; comandos publicam eventos; eventos disparam efeitos colaterais (jobs).

Os comandos centrais (`IngestInboundMessage`, `CompleteTriagem`, `GiveConsent`, `RevokeConsent`) precisam:

1. persistir uma decisão de domínio;
2. registrar **o que aconteceu** de forma auditável (LGPD, prestação de contas a municípios);
3. acionar consumidores (jobs) sem acoplamento direto entre quem publica e quem consome.

Alternativas reais:

- chamar `Job.perform_later` direto do comando — acopla, polui o comando com lista de consumidores, dificulta replay e auditoria;
- Active Record callbacks — esconde a publicação, propenso a recursão e double-fire;
- pub/sub externo (Kafka, NATS) — desproporcional para a carga; adiciona dependência crítica fora do Postgres ([ADR-0001](0001.md) explicitamente quis evitar isso).

## Decisão

Padrão **outbox-leve sobre Postgres** com três peças:

### 1. Tabela `domain_events` (auditoria + replay)

Toda publicação grava uma linha:

| coluna         | tipo                | nota                                              |
|----------------|---------------------|---------------------------------------------------|
| `id`           | uuid                | gerado pelo app                                   |
| `name`         | string              | `triagem.completed`, `consent.given`, ...         |
| `aggregate_type` | string            | `Triagem`, `Conversation`, ...                    |
| `aggregate_id` | string              | id do agregado                                    |
| `payload`      | jsonb               | dados imutáveis                                   |
| `occurred_at`  | timestamptz         | quando, em UTC                                    |
| `published_at` | timestamptz null    | quando os bindings foram disparados               |

`published_at` separa "evento registrado" de "consumidores notificados", o que permite o replay descrito em [ADR-0009](0009.md).

### 2. Publisher `Events.publish(name, aggregate:, payload:)`

API única usada pelos comandos:

```ruby
Events.publish(
  "triagem.completed",
  aggregate: triagem,
  payload: { tier: outcome.tier, priority: outcome.priority }
)
```

A implementação:

1. insere `DomainEvent` na transação corrente;
2. olha o registro de bindings (passo 3) e enfileira cada job alvo;
3. graças ao [ADR-0004](0004.md), nada chega ao worker antes do COMMIT;
4. quando o consumidor termina com sucesso, atualiza `published_at` (best-effort — replay sabe lidar com null).

### 3. Tabela de bindings declarativa

`config/initializers/domain_events.rb` registra `event_name => [job_class, ...]`:

```ruby
Events.bind "inbound_message.received", to: ProcessInboundMessageJob
Events.bind "triagem.completed",        to: [GenerateReportJob, UpdateDashboardJob, NotifyCitizenJob]
Events.bind "triagem.urgent",           to: AlertMunicipalityJob
Events.bind "consent.given",            to: []  # só audita
Events.bind "consent.revoked",          to: []
```

Bindings são lidos uma única vez no boot. Adicionar consumidor = uma linha no initializer + `queue_as` no job. Remover consumidor = apagar a linha; a auditoria permanece.

## Consequências

Positivas:

- comandos ficam limpos: publicam um evento, ponto. Consumidores são detalhe de infra;
- auditoria completa por construção — `SELECT * FROM domain_events WHERE aggregate_id = ?` é a história;
- replay e reenfileiramento ([ADR-0009](0009.md)) viram queries simples sobre `published_at IS NULL`;
- novo consumidor não precisa tocar o comando — só o initializer.

Negativas / a vigiar:

- ordem global de eventos não é garantida entre agregados; ordem **dentro** de um agregado vem da transação. Aceitável para nosso domínio;
- `published_at` é best-effort: se o worker cair entre dispatch e update, o evento parece "não publicado" e pode ser reenfileirado por [ADR-0009](0009.md). Por isso os consumidores **precisam ser idempotentes** ([ADR-0005](0005.md));
- payload imutável significa migração de schema do evento exige versão (`name` com sufixo `.v2` ou campo `schema_version` no payload).

## Convenções de nomenclatura

- nomes em minúsculo, `aggregate.action_passado` — `triagem.completed`, `consent.revoked`;
- nunca o nome do consumidor (`generate_report`) — o evento descreve fato, não intenção;
- payload contém apenas dados, não objetos AR;
- `aggregate_id` sempre o id externo (uuid), nunca o id interno mutável.

## Alternativas consideradas

- **Wisper / event_bus em memória** — perde auditoria, perde replay, perde garantia transacional;
- **Outbox pattern completo com relay process** — overhead operacional, não justificado enquanto consumidores forem in-cluster;
- **Sidekiq middleware** — específico de Sidekiq, descartado por [ADR-0001](0001.md).

## Revisão

Reavaliar se:

- algum consumidor precisar viver fora do cluster (microserviço externo) — então o relay vira necessário;
- volume de `domain_events` passar de ~10⁷ linhas/mês por município — particionar por mês.
