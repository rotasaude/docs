# ADR-0019 — Isolamento multi-tenant: Row-Level Security no Postgres
- **Status:** Aceita
- **Data:** 2026-06-20
- **Contexto:** Rota Saúde (piloto municipal)
- **Toca:** ADR 0001 (fila no mesmo Postgres)
- **Relacionado:** ADR 0016 (`municipality_id`), ADR 0007 (projeções), ADR 0009
  (auditoria). Base das emendas 0020 e 0021.
## Contexto
Decidida a **instalação única multi-tenant**: uma stack serve todos os
municípios, `municipality_id` distingue tenant. Isso coloca dado clínico de
todas as cidades — `triages`, `conversations`, `consents`, `report_snapshots` —
nas mesmas tabelas do mesmo banco. Hoje só `protocols` (0016) tem escopo de
tenant; o resto é cego a tenant.
Num desenho assim, um `where(municipality_id:)` esquecido não é bug cosmético:
é cidade A lendo cidadão de saúde da cidade B — incidente LGPD reportável.
Escopo só na aplicação deixa a única rede de proteção na disciplina de quem
escreve a query.
## Decisão
Isolamento imposto pelo **Postgres via Row-Level Security**, não só por escopo
de aplicação. O banco filtra por `municipality_id` independentemente de bug na
camada Ruby. "Esquecer o where" deixa de vazar.
### Variável de tenant transação-local
Políticas filtram por uma variável de sessão, setada por transação:
```sql
ALTER TABLE triages ENABLE ROW LEVEL SECURITY;
ALTER TABLE triages FORCE  ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON triages
  USING      (municipality_id = current_setting('app.municipality_id')::bigint)
  WITH CHECK (municipality_id = current_setting('app.municipality_id')::bigint);
```
- **`SET LOCAL app.municipality_id = '<id>'`**, sempre **dentro de transação** —
  reseta no COMMIT/ROLLBACK. `SET` puro persiste na conexão do pool e vaza para
  o próximo request que reusar a conexão.
- **`WITH CHECK`** impede *gravar* linha de outro tenant, não só ler.
- **`FORCE ROW LEVEL SECURITY`** é obrigatório: o dono da tabela ignora RLS por
  padrão, e o Rails normalmente conecta como dono. Sem FORCE, a política não
  vale para a própria aplicação.
### Dois papéis de banco
| Papel | Atributo | Usado por |
|---|---|---|
| `rota_app` | sujeito a RLS (FORCE) | caminho web e jobs de domínio — todo trabalho escopado por tenant |
| `rota_admin` | `BYPASSRLS` | recurring tasks, contexto-operador, migrations — cross-tenant legítimo |
Bypass via **papel separado**, não via variável (`OR current_setting('app.bypass')`
na política). Esquecer o `OR` numa política cegaria o operador naquela tabela; um
bug no bypass-var seria permissivo demais. O papel é Postgres-nativo e à prova de
esquecimento. Custo: **duas conexões** — `database.yml` declara `primary`
(`rota_app`) e `admin` (`rota_admin`); jobs privilegiados usam `connected_to`.
### Quais tabelas recebem RLS
Toda tabela com `municipality_id` e dado de tenant: `triages`, `conversations`,
`inbound_messages`, `consents`, `report_snapshots`, `dashboard_metrics`,
`domain_events`, `processed_events`, e `protocols` (já escopada no 0016, agora
**imposta** por política).
**Exceção — `municipality_channels`.** A tabela de roteamento
(`phone_number_id` → `municipality_id`, ADR 0021) **não pode** ser tenant-scoped:
no momento em que é lida, ainda não se sabe o município — é justamente o que se
vai descobrir. É config, lida fora de escopo de tenant para *estabelecer* o
escopo. Sem política de `municipality_id`; acesso de leitura controlado por papel.
### A fronteira da Solid Queue
A fila vive no mesmo Postgres (0001), mas `solid_queue_*` guarda jobs de
**todas** as cidades. **Nenhuma política de tenant nessas tabelas** — política
ali quebraria o despacho. Há dois contextos distintos:
- **Máquina de fila** — enfileirar, fazer poll, reclamar job: tenant-agnóstica,
  sem RLS.
- **Corpo do job** — o que o `perform` faz com dado de domínio: tenant-scoped,
  seta a variável no início (ADR 0020).
Errar essa linha ou trava a fila (política nas tabelas dela) ou vaza tenant
(corpo sem variável).
### Caminho web
`around_action` em `ApplicationController` resolve o município do usuário
autenticado (membership, ADR 0023) ou do tenant selecionado pelo operador, abre
transação e faz `SET LOCAL`:
```ruby
around_action :within_tenant
def within_tenant
  ApplicationRecord.transaction do
    Current.municipality_id = current_municipality.id
    ApplicationRecord.connection.execute(
      ApplicationRecord.sanitize_sql(
        ["SET LOCAL app.municipality_id = ?", current_municipality.id]
      )
    )
    yield
  end
end
```
Leitura fora de transação perderia o `SET LOCAL` — por isso o request escopado
roda dentro da transação do `around_action`. O caminho worker é tratado no 0020.
### Caminho das recurring tasks
Purge de `raw` (0011), de `domain_events` (0009), varredura de timeout (0012) e
reconciliação (0007) varrem todas as cidades — rodam como **`rota_admin`**
(bypass). É o uso legítimo do papel privilegiado.
## Invariantes
- **Nenhuma query de domínio roda sem tenant setado.** `rota_app` sem
  `app.municipality_id` → `current_setting` levanta, a query falha barulhento.
  Falha **fechada**, não aberta: ausência de tenant nega, não libera.
- **Cross-tenant é explícito.** Atravessar tenant exige `rota_admin`
  conscientemente. Não há caminho acidental.
## Consequências
- O invariante de isolamento vira **testável no nível do banco**: setar tenant A
  e tentar ler linha de B deve voltar vazio. Cobre a dimensão de isolamento da
  lacuna de testes (§2.4 da nota) — não as outras.
- Operação ganha **dois papéis / duas conexões** para administrar. Migrations
  rodam como `rota_admin`.
- `dashboard_metrics` (0007) é escopada por política; visão agregada cross-tenant
  do operador roda sob bypass com `GROUP BY municipality_id`.
- `processed_events` (0005) ganha `municipality_id` por consistência; o índice
  único segue `(event_id, consumer)` — detalhe no 0020.
## Em aberto
- **Retenção por município.** O 0009 fixou TTL de 12 meses "revisável quando o
  município se manifestar". Multi-tenant abre TTL divergente por cidade; o purge
  respeitaria config por-município. Fora do MVP — evolução, não decidido aqui.
- **Visões agregadas do operador** (cross-tenant): existem sob bypass, mas quais
  métricas o operador de plataforma vê é trabalho do tier de plataforma
  (ADR 0023), não deste ADR.
