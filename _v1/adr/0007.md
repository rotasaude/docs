# ADR-0007 — Relatórios congelados e dashboard reconstrutível

- Status: Accepted
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0003](0003.md) (eventos), [ADR-0009](0009.md) (replay), [ADR-0013](0013.md) (motor), [ADR-0015](0015.md) (Outcome), [ADR-0016](0016.md) (storage de protocolos)

## Contexto

Triagem termina, e três coisas precisam acontecer:

1. **Cidadão recebe um link** `GET /r/:token` com o desfecho da triagem (tier, recomendação, próximos passos) — público, sem login, válido por dias;
2. **Secretaria municipal vê painéis** agregados (quantas triagens por tier, evolução por dia, fila de urgentes pendentes);
3. **Time clínico consegue revisar** uma triagem antiga **exatamente** como ela foi calculada — mesmo que o protocolo já tenha sido modificado depois.

Os três têm requisitos diferentes:

- relatório individual: **imutável** depois de gerado; reproduzível mesmo se o protocolo mudar;
- dashboard agregado: **fresco** o suficiente para tomar decisão, **reconstrutível** se as métricas se corromperem;
- revisão histórica: **fiel** à definição usada na época, não à versão atual.

## Decisão

Duas estruturas distintas, com fontes da verdade diferentes:

### 1. `ReportSnapshot` — congelado, imutável

Após `triagem.completed`, `GenerateReportJob` cria um `ReportSnapshot` que congela:

| coluna                       | tipo         | nota                                          |
|------------------------------|--------------|-----------------------------------------------|
| `id`                         | uuid         |                                               |
| `triagem_id`                 | uuid         |                                               |
| `protocol_definition_id`     | uuid         | versão exata usada (ADR-0016)                 |
| `outcome`                    | jsonb        | `Outcome.to_h` (ADR-0015) — tier/priority/trail |
| `payload`                    | jsonb        | resposta human-readable (templates aplicados) |
| `token`                      | string       | url-safe, único, indexado                     |
| `signature`                  | string       | HMAC do token com `REPORT_SIGNING_KEY`        |
| `expires_at`                 | timestamptz  |                                               |
| `created_at`                 | timestamptz  |                                               |

`payload` é congelado: mesmo que o template ou o protocolo mudem amanhã, o que o cidadão vê em `GET /r/:token` é o que foi gerado hoje.

`token` + `signature` evita varredura: rota verifica HMAC antes de buscar no banco. `expires_at` permite expirar links sem deletar dados (auditoria preservada).

`ReportsController#show` é o único endpoint público; verifica `signature`, checa `expires_at`, renderiza `payload`.

### 2. `DashboardMetric` — agregado, reconstrutível

Tabela com linhas pré-agregadas por `(municipality_id, dimension, period)`:

| coluna           | tipo         | exemplo                                  |
|------------------|--------------|------------------------------------------|
| `municipality_id`| uuid         |                                          |
| `dimension`      | string       | `triagens_by_tier`, `urgent_pending`     |
| `period`         | string       | `2026-06-18`, `2026-W24`, `2026-06`      |
| `key`            | string       | sub-chave (`alta`, `media`, `baixa`)     |
| `value`          | integer      | contagem ou soma                          |
| `updated_at`     | timestamptz  |                                          |

Atualização **incremental** vem de `UpdateDashboardJob`, consumidor de `triagem.completed` ([ADR-0003](0003.md)). Cada evento processado faz `INSERT … ON CONFLICT … DO UPDATE` em algumas linhas. Sem locks longos.

Reconstrução **completa** vem de `scripts/rebuild_dashboard_metrics.rb`, executado pelo `recurring.yml` (nightly), que:

1. `TRUNCATE` das linhas de `dashboard_metrics`;
2. lê tudo de `triagens` (e tabelas relacionadas) — fonte da verdade;
3. recalcula agregado por agregado;
4. `INSERT` em batch.

Esse script é o que garante que **as métricas convergem para a verdade dos fatos** mesmo que algum `UpdateDashboardJob` tenha falhado, sido reenfileirado ou ficado fora de ordem.

### 3. Notificação ao cidadão e alerta à secretaria

- `NotifyCitizenJob` consome `triagem.completed`, busca o snapshot, monta a URL assinada e enfileira `SendWhatsappJob` ([ADR-0014](0014.md));
- `AlertMunicipalityJob` consome `triagem.urgent` na fila `urgent` ([ADR-0008](0008.md)); chama a secretaria via canal definido por município (hoje: e-mail; futuro: webhook).

Ambos são `IdempotentConsumer` ([ADR-0005](0005.md)).

## Consequências

Positivas:

- relatório individual é **prova** do que aconteceu, não interpretação atualizada — atende auditoria e responsabilização clínica;
- dashboard fica simples e rápido em consulta (linhas pré-agregadas);
- corrupção em métricas tem caminho de cura óbvio: rodar `rebuild_dashboard_metrics.rb` — sem precisar entender o que falhou;
- desacoplamento total entre os três caminhos (snapshot vs métrica vs notificação) — falha em um não afeta os outros.

Negativas / a vigiar:

- duplicação de informação: dado existe em `triagens` (cru) e em `dashboard_metrics` (agregado). Aceitamos porque reconstrução é trivial;
- `payload` do snapshot precisa ser pequeno suficiente para caber em jsonb com performance razoável (~10KB) — protocolos com trail longo precisam de poda no payload (não no `outcome.trail`);
- HMAC de token assume `REPORT_SIGNING_KEY` em `Rails.application.credentials` ([ADR-0011](0011.md)) — rotação exige aceitar duas chaves por janela. Implementar quando necessário.

## Recurring (limpeza e reconstrução)

`config/recurring.yml` (Solid Queue 1.0+):

```yaml
production:
  rebuild_dashboard_metrics:
    class: RebuildDashboardMetricsJob
    schedule: every day at 3am America/Sao_Paulo
  purge_expired_reports:
    class: PurgeExpiredReportsJob
    schedule: every day at 4am America/Sao_Paulo
  purge_processed_events:
    class: PurgeProcessedEventsJob
    schedule: every day at 4:30am America/Sao_Paulo
  reconcile_consents:
    class: ReconcileConsentsJob
    schedule: every day at 5am America/Sao_Paulo
```

O script de reconstrução fica disponível também como `bin/rails runner scripts/rebuild_dashboard_metrics.rb` para uso manual em incidente.

## Alternativas consideradas

- **Renderizar relatório sob demanda a partir da triagem viva** — quebra imutabilidade; muda quando o protocolo muda; perde para auditoria;
- **Dashboard via query em tempo real** — funciona enquanto base for pequena; degrada rápido;
- **Materialized views do Postgres para dashboard** — atrativo, mas `REFRESH MATERIALIZED VIEW` em janela operacional já cobre o caso sem dependência de feature avançada do Postgres.

## Revisão

Reavaliar se:

- snapshot crescer demais para caber em jsonb confortavelmente — extrair `payload` para `blob`/object storage;
- dashboard precisar de fatias por médico/posto — adicionar `key` composto ou tabela específica;
- caminhos de notificação se diversificarem além de WhatsApp/e-mail — abstrair `Notify::Channel`.
