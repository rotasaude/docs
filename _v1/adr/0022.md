# ADR-0022 — Autenticação, sessão e MFA

* Status: Aceita
* Data: 2026-06-20
* Contexto: Rota Saúde (piloto municipal)
* Fecha: §2.1 da nota de revisão (autenticação dos usuários da municipalidade — ausente).
* Relacionado: ADR 0016 (publisher / ato de publicação), ADR 0019 (resolução de tenant a partir de membership), ADR 0023 (memberships, tier de plataforma, autorização), ADR 0009 (auditoria).

## Contexto
O 0016 definiu roles (`protocol_author`, `protocol_publisher`) mas nenhum ADR diz como essas pessoas autenticam. Num sistema onde "publicar" empurra lógica clínica para produção, a ausência de história de auth é buraco real (§2.1).
Staff não é cidadão. O cidadão autentica por posse do telefone + consentimento (0012); não tem senha, não tem conta aqui. Este ADR é só sobre usuários da municipalidade e o operador de plataforma. (A reconciliação de identidade do cidadão com CNS/SUS é o §2.5, separado.)

## Decisão
Autenticação nativa do Rails 8 (`has_secure_password` + o gerador de authentication: `Session`, reset de senha, `Current.user`/`Current.session`), com seam para gov.br (OIDC) e MFA (TOTP) em dois pontos: login do operador e ato de publicação do publisher.

### Por que nativo
Mesma lógica do 0001 (Solid Queue sobre RabbitMQ): o embutido vence no piloto. Sem dependência externa, sem provedor de identidade para administrar. O gerador do Rails 8 entrega sessão em banco, reset por token assinado e o `Authentication` concern prontos.
gov.br fica adiado, não fechado. É a opção natural para servidor público (provavelmente já tem conta) e dá MFA de graça via os selos de confiabilidade (bronze/prata/ouro). O seam abaixo deixa gov.br entrar sem reescrever sessão nem autorização.

### Identidade é global — fora do RLS
Ponto estrutural: um usuário pode servir mais de uma cidade (via memberships, 0023) e o operador não pertence a nenhuma. Logo a identidade não é tenant-scoped:

* `users`, `sessions`, `identities` são RLS-exempt (como `municipality_channels`, 0019). Login roda antes de qualquer tenant estar resolvido.
* Auth responde quem; membership (0023) responde qual cidade e qual papel. Só depois do login o `around_action` (0019) resolve `current_municipality` do membership e faz o `SET LOCAL`.
* Como `users` é RLS-exempt, a separação entre cidades na gestão de usuários é responsabilidade da autorização (0023), não do banco: um admin municipal só enxerga usuários via `memberships` da sua cidade. Esse handoff precisa ser à prova de vazamento — é o gêmeo, no lado da identidade, da exceção de `municipality_channels`.

```
users        email, password_digest, otp_secret (encrypts), otp_enabled, ...
sessions     user_id, ip_address, user_agent, ...        # gerador do Rails 8
identities   user_id, provider, provider_uid             # seam; 'password' hoje
```

### Sessão e fluxo
O gerador do Rails 8 dá `SessionsController` (login/logout), `PasswordsController` (reset por e-mail via ActionMailer) e o `Authentication` concern (`require_authentication`). Os endpoints de auth não rodam dentro do `within_tenant` (0019) — não há tenant ainda. Depois de autenticado, o request normal resolve o tenant do membership.

### MFA (TOTP) em dois pontos
TOTP (RFC 6238), `otp_secret` encriptado, com recovery codes para perda do dispositivo.

* **Operador de plataforma** — MFA no login, obrigatório. É o alvo de maior valor: lê dado de toda cidade, cria admins, gira a chave que protege todos os tokens (0024). Sem MFA o tier de plataforma não loga.
* **Publisher** — step-up no ato de publicar. Não em todo login: re-autentica com TOTP no momento de publicar um protocolo (0016). Liga direto na exigência do 0016 de que publicação é ato distinto com "reabertura/confirmação explícita no controller" — o step-up é essa reabertura, agora com segundo fator.

```ruby
# PublicationsController (0016) — publicar exige step-up do publisher
def create
  return mfa_challenge unless reauthenticated_recently?(via: :totp)
  Protocols::Publish.call(version: params[:version], by: Current.user)  # registra published_by
end
```

Proporcionalidade: MFA pesa onde o risco clínico está (empurrar protocolo para prod), não em toda interação.

### O seam do gov.br
Autenticação atrás de um ponto único, para gov.br entrar como estratégia nova, não como reescrita:

```ruby
# app/auth/authenticator.rb
module Authenticator
  def self.password(email:, password:)
    user = User.find_by(email:)
    user if user&.authenticate(password)        # has_secure_password
  end
  # def self.govbr(code:) = ...  # futuro: troca o code OIDC por Identity federada
end
```

Quando gov.br entrar: adiciona-se uma estratégia + uma linha em `identities` (`provider: 'govbr'`), e o `Session` é criado igual. Hook de futuro: exigir selo prata/ouro do gov.br para quem for `protocol_publisher` — assurance de identidade proporcional à consequência clínica.

### Auditoria

* Mudança de papel (conceder/revogar `author`/`publisher`) é tenant-scoped (acontece numa cidade) → vai pelo `DomainEvents.publish` normal sob aquele tenant (0020); desenho no 0023.
* Eventos puros de identidade (login, logout, falha de login, enrollment de MFA, reset de senha) são platform-scope — acontecem antes de haver tenant. Não cabem no `publish` tenant-scoped (0020 levanta `TenantMissing` sem tenant). O canal de auditoria platform-scope é formalizado junto com o tier de plataforma no 0023.

## Consequências

* Identidade (global) e autorização (por-tenant) ficam em camadas separadas: 0022 autentica, 0023 autoriza. Trocar o provedor de auth (gov.br) não toca a autorização.
* `users` RLS-exempt transfere a responsabilidade de isolamento, na gestão de usuários, para a autorização do 0023 — explicitado lá.

## Em aberto

* Integração gov.br propriamente (endpoints OIDC, mapa de selo → papel): ADR próprio quando sair do piloto-só-senha.
* Recovery de MFA (fluxo de perda de dispositivo além dos recovery codes — ex.: reset assistido pelo operador).
* Canal de auditoria platform-scope (eventos de identidade): 0023.
