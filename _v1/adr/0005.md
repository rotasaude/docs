# ADR-0005 — Idempotência de consumidores via `processed_events`

- Status: Accepted
- Data: 2026-06-18
- Decisores: time rota-saúde
- Relacionados: [ADR-0003](0003.md) (eventos), [ADR-0004](0004.md) (commit-then-enqueue), [ADR-0009](0009.md) (replay), [ADR-0010](0010.md) (webhook ack), [ADR-0014](0014.md) (HTTP fora do lock)

## Contexto

O sistema tem três fontes naturais de re-entrega:

1. **Webhook do WhatsApp** entrega o mesmo evento mais de uma vez quando demoramos a responder 200 OK ([ADR-0010](0010.md));
2. **Solid Queue** reenfileira automaticamente jobs que excedem timeout ou crasham o worker;
3. **Reenfileiramento manual** dos eventos pendentes em `domain_events` ([ADR-0009](0009.md)) para recuperar consumidores que falharam silenciosamente.

Sem proteção, qualquer dos três produz **efeitos duplicados**:

- mesma mensagem registrada N vezes;
- WhatsApp recebe o mesmo template N vezes (cidadão irritado, custo, possível ban);
- secretaria recebe N alertas para a mesma triagem urgente;
- dashboard conta a mesma triagem N vezes.

O domínio é incompatível com "at-least-once com efeitos colaterais idempotentes na hora", porque parte dos efeitos é externa (mensagem no WhatsApp) e não é naturalmente idempotente.

## Decisão

Adotar **exactly-once por consumidor** via tabela `processed_events` com chave única composta:

| coluna         | tipo         | nota                                  |
|----------------|--------------|---------------------------------------|
| `consumer`     | string       | nome do job (`SendWhatsappJob`)       |
| `event_id`     | uuid         | id do `domain_events` consumido       |
| `processed_at` | timestamptz  | quando entrou                         |

Índice único em `(consumer, event_id)`.

Cada consumidor herda do concern `IdempotentConsumer`:

```ruby
class ProcessInboundMessageJob < ApplicationJob
  include IdempotentConsumer
  queue_as :realtime

  def consume(event)
    # idempotent body — só roda se o INSERT em processed_events teve sucesso
  end
end
```

O `perform` do concern:

1. abre transação;
2. tenta `INSERT` em `processed_events`;
3. se cair na constraint única → retorna sem fazer nada (já processado);
4. se entrar → chama `consume(event)`;
5. commit. Falha em `consume` faz rollback do INSERT também — job pode ser retentado.

Para o webhook ([ADR-0010](0010.md)) usamos a mesma tabela, mas com `consumer = "whatsapp_webhook"` e `event_id` derivado do `message_id`/`change_id` que a Meta envia. Isso desduplica antes mesmo de virar `DomainEvent`.

## Consequências

Positivas:

- garantia exactly-once por consumidor sem coordenação externa;
- protege simultaneamente contra retry do worker, replay manual e duplicata do WhatsApp;
- `processed_events` também é trilha de auditoria: "quem consumiu o quê e quando";
- combinado com [ADR-0003](0003.md) + [ADR-0004](0004.md), o sistema inteiro se comporta como "evento → ação" determinístico.

Negativas / a vigiar:

- tabela cresce indefinidamente. Mitigamos com purga em `recurring.yml` de linhas com `processed_at < N dias` (N maior que a janela de replay possível);
- o `consume` precisa ser **transacional**: qualquer escrita em outras tabelas tem que ficar dentro da transação aberta pelo concern. Side-effects fora do banco (chamada HTTP) **não** podem ficar dentro — vão para job separado, daí [ADR-0014](0014.md);
- erros em `consume` rebobinam o INSERT — não esquecer disso ao calcular retry count na UI;
- a chave única exige `event_id` real (uuid do `DomainEvent`); jobs que não vêm de evento (raros) precisam adotar outra chave idempotente explícita.

## Padrão de uso

```ruby
class NotifyCitizenJob < ApplicationJob
  include IdempotentConsumer
  queue_as :default

  def consume(event)
    triagem = Triagem.find(event.aggregate_id)
    # ... lógica idempotente ...
  end
end
```

Toda criação de job consumidor é feita assim. Jobs que **não** consomem evento (raríssimos) não incluem o concern, e levam comentário explicando por quê.

## Alternativas consideradas

- **Idempotência ad-hoc por consumidor** (cada um faz `find_or_create_by`) — fragmenta, fácil de errar, sem auditoria centralizada;
- **Distributed lock por aggregate_id** — não protege contra duplicata cross-aggregate; adiciona ponto de contenção;
- **Outbox completo com offset por consumidor** — equivalente em garantia, mas mais máquina pra construir do que valor entregue hoje.

## Revisão

Reavaliar se:

- algum consumidor precisar processar **fora** do Postgres (microserviço externo) — então a tabela vira insuficiente e precisamos de offset distribuído;
- a purga não conseguir acompanhar o crescimento — partitioning por mês.
