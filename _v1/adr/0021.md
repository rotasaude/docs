# ADR-0021 — Roteamento de canal e ingestão multi-tenant (emenda aos ADR 0010, 0011, 0012)

* Status: Aceita
* Data: 2026-06-20
* Contexto: Rota Saúde (piloto municipal)
* Emenda: ADR 0010 (ingestão), ADR 0011 (`inbound_messages`), ADR 0012 (`Conversation.for`, índice de conversa ativa)
* Relacionado: ADR 0019 (RLS, tabela de roteamento exempt), ADR 0020 (tenant em jobs), ADR 0024 (custódia da credencial WhatsApp).

## Contexto
Instalação única multi-tenant (0019): uma stack, todos os municípios. Cada cidade tem seu número de WhatsApp. O webhook (0010) é único — todas as cidades caem no mesmo endpoint. Falta o passo que diz de qual cidade é esta mensagem, e esse passo precisa rodar antes de qualquer persistência sob RLS.
Além disso, `Conversation.for(phone)` (0012) nunca carregou município, mas `Protocols.current` (0016) exige um. Esse gap latente fecha aqui.

### Topologia do Meta App: um App, vários números
Um Meta App, vários `phone_number_id` (multi-tenant também no Meta):

* Um App Secret valida o HMAC (`X-Hub-Signature-256`, 0010) de todos os webhooks — fica no env (0018), compartilhado entre tenants.
* Um verify token (challenge GET de setup) e uma webhook URL, App-level.
* Número de cidade nova entra pela WABA sem provisionar App novo.
* O access token de envio é por-número (por-cidade), e segue encriptado no banco — custódia no ADR 0024.

Blast radius assumido: suspensão do App afeta todas as cidades. Risco do operador único, aceito no piloto.
A ordem na borda passa a ser três passos: HMAC (é mesmo o Meta?) → rota (qual cidade?) → persiste (sob o tenant resolvido).

### `municipality_channels` — a tabela de roteamento

```
municipality_channels
  id                    bigserial
  municipality_id       bigint
  phone_number_id       text        # id do número no Meta — ÚNICO
  waba_id               text        # WhatsApp Business Account
  display_phone_number  text        # +55... legível
  access_token          text        # secret de envio, encrypts (custódia → 0024)
  active                boolean
  created_at, updated_at
```

Índice único em `phone_number_id` (um número → uma cidade). Sem RLS (0019): é a tabela que estabelece o tenant, lida antes de saber o tenant. O `access_token` é secret de canal (`encrypts`); onde a chave vive e como rotaciona é do 0024.

### Emenda ao ADR 0010 — ingestão resolve e carimba o tenant
Roteia por change (o `phone_number_id` vive em `value.metadata`, comum às mensagens daquela mudança), seta `SET LOCAL` por transação e carimba `municipality_id` no inbound e no enqueue.

```ruby
# app/services/whatsapp/ingest.rb  (substitui o do ADR 0010)
module Whatsapp
  class Ingest
    def self.call(payload) = new(payload).call
    def initialize(payload) = (@payload = payload)

    def call
      changes.each do |change|
        municipality_id = route(change)
        next unless municipality_id            # número desconhecido — já parqueado

        messages_in(change).each do |msg|
          ApplicationRecord.transaction do
            Current.municipality_id = municipality_id
            ApplicationRecord.connection.execute(
              ApplicationRecord.sanitize_sql(["SET LOCAL app.municipality_id = ?", municipality_id])
            )
            inbound = InboundMessage.create!(
              provider_message_id: msg[:id],     # wamid — índice único
              municipality_id:,
              from:                msg[:from],
              raw:                 msg,          # criptografado + retido curto (0011)
              status:              :pending
            )
            ProcessInboundMessageJob.perform_later(inbound.id, municipality_id:)
          end
        rescue ActiveRecord::RecordNotUnique
          next                                   # reentrega do mesmo wamid — já ingerido
        end
      end
    end

    private

    def route(change)
      pnid    = change.dig(:value, :metadata, :phone_number_id)
      channel = MunicipalityChannel.active.find_by(phone_number_id: pnid)
      return channel.municipality_id if channel

      UnknownChannel.record!(phone_number_id: pnid, change:)  # parking + alerta operador
      nil
    end

    def changes      = Array(@payload[:entry]).flat_map { |e| Array(e[:changes]) }
    def messages_in(c) = Array(c.dig(:value, :messages))
  end
end
```

`route` lê `municipality_channels` sem tenant setado — a tabela é RLS-exempt, então isso é seguro e necessário (é o que descobre o tenant). Só depois o `SET LOCAL` entra, para a persistência do inbound sob RLS.

### Número desconhecido
`phone_number_id` que não casa nenhum canal: o HMAC passou (é Meta de verdade, nosso App), mas o número não está provisionado. É misconfiguração, não ataque. Política: ack 200 (não fazer o Meta reentregar um erro de config indefinidamente), parquear em `unknown_channels` e alertar o operador. Não processa. Novo modo de falha que a borda passa a tratar.
`statuses[]` (recibos das mensagens que enviamos) roteia pelo mesmo `phone_number_id`; o processamento deles (atualizar estado de entrega do outbound) fica fora do escopo deste ADR.

### Emenda ao ADR 0011 — `inbound_messages` ganha tenant
* Coluna `municipality_id` (carimbada na ingestão), tabela passa a ter RLS (0019).
* Criptografia do `raw` inalterada: Active Record Encryption com chave global (env, 0018) protege o `raw` de todos os tenants em repouso; o acesso é isolado por RLS. O purge do `raw` (recurring task, 0011) roda cross-tenant sob `rota_admin` (bypass, 0019).

### Emenda ao ADR 0012 — `Conversation.for` recebe município

```ruby
# app/models/conversation.rb  (emenda ao ADR 0012)
def self.for(phone, municipality_id:)
  active.find_by(municipality_id:, phone:) || create!(
    municipality_id:, phone:,
    status:           :awaiting_consent,
    consent_version:  Consents.current_version(municipality_id),
    protocol_version: Protocols.current(municipality_id).version
  )
end
```

* Índice único parcial de conversa ativa passa de `phone` para `(municipality_id, phone)` nos status `awaiting_consent`/`in_progress`. Um mesmo telefone pode ter conversa viva em duas cidades distintas (cidadão de divisa, número compartilhado) — são tenants diferentes, conversas independentes.
* `Consents.current_version` e `Protocols.current` passam a receber `municipality_id`: termos de consentimento (0024) e protocolo (0016) são por-cidade.

O `ProcessInboundMessageJob` (0010/0014) recebe `municipality_id`, abre com `with_tenant` (0020) e repassa para o `Conversation.for` e o `SendWhatsappJob`:

```ruby
# app/jobs/process_inbound_message_job.rb  (emenda — tenant via 0020)
class ProcessInboundMessageJob < ApplicationJob
  include TenantScopedJob

  def perform(inbound_message_id, municipality_id:)
    with_tenant(municipality_id) do
      inbound = InboundMessage.find(inbound_message_id)
      return if inbound.processed?

      conversation = Conversation.for(inbound.from, municipality_id:)
      conversation.with_lock do
        result = conversation.advance(inbound)
        inbound.update!(status: :processed)
        CompleteTriage.call(**result.triage_args) if result.completes_triage?
        SendWhatsappJob.perform_later(to: inbound.from, body: result.reply, municipality_id:) if result.reply
      end
    end
  end
end
```

### O custo da exceção RLS: escopo manual na tabela de roteamento
`municipality_channels` é RLS-exempt, então queries contra ela não ganham o filtro automático — é o único lugar onde "lembrar o where" volta. O `SendWhatsappJob`, que precisa do número e do token da cidade para enviar, escopa à mão:

```ruby
class SendWhatsappJob < ApplicationJob
  include TenantScopedJob
  def perform(to:, body:, municipality_id:)
    with_tenant(municipality_id) do
      channel = MunicipalityChannel.find_by!(municipality_id:, active: true)  # escopo manual
      Whatsapp::Outbound.new(channel).deliver_text(to:, body:)
    end
  end
end
```

Risco mitigado por ser uma tabela estreita com escopo manual explícito, não espalhado pelo domínio. Vale teste dedicado.

## Invariantes

* Tenant resolvido na borda, nunca adivinhado depois. A cadeia `phone_number_id → municipality_id` é decidida uma vez, na ingestão, e viaja como argumento (0020) por todo o processamento.
* Três fontes de tenant, um destino. Web resolve de membership (0019/0023); ingestão resolve de `phone_number_id`; job resolve de argumento (0020). Todas setam o mesmo `app.municipality_id`.

## Consequências

* A borda ganha um passo de I/O em banco (lookup de canal) antes de persistir — trivial, índice único em `phone_number_id`.
* Outbound depende do canal certo: no piloto, um canal ativo por cidade. Múltiplos canais por município são permitidos pelo schema mas a seleção de canal no envio fica indefinida — fora de escopo.

## Em aberto

* Corrida de primeiro contato (§3.3 da nota). Dois inbounds do mesmo telefone disparam dois `create!` de conversa; o índice `(municipality_id, phone)` levanta em um. A correção segue sendo índice + retry do job — documentada agora, mas o tratamento explícito do `RecordNotUnique` em `for` permanece como item à parte.
* Custódia/rotação do `access_token` de canal e da chave do AR Encryption: ADR 0024.
* Seleção de canal no outbound quando uma cidade tiver mais de um número.
