# ADR 0003 — Multi-tenant isolation (Row-Level Security)

- **Status:** Substituída pelo [ADR 0020](0020.md) (banco por cidade)
- **Data:** 2026-06-23
- **Contexto:** Rota Saúde

## Decisão

O Rota Saúde é uma **instalação única multi-tenant**: uma stack serve todos os
municípios, e `municipality_id` distingue o tenant. O isolamento entre cidades é
**imposto pelo Postgres via Row-Level Security**, não apenas por escopo de
aplicação. Um `where(municipality_id:)` esquecido na camada Ruby não vaza — o banco
filtra por conta própria; "esquecer o where" deixa de ser incidente de LGPD.

A separação estruturante é **control plane vs data plane**:

- **Data plane** — dado de domínio do tenant (`triages`, `conversations`,
  `consents`, ...). **RLS-enforced**.
- **Control plane** — tabelas que existem para **resolver ou autorizar** o tenant
  (roteamento, identidade, membership, registro de município). Lidas **antes** de
  haver tenant, logo **RLS-exempt**, protegidas pela autorização da aplicação
  (ADR 0012).

O risco de "esquecer o where" fica concentrado no control plane — um conjunto
pequeno, nomeado e auditável de tabelas — em vez de espalhado pelo domínio.

## Detalhamento

**Variável de tenant transação-local.** As políticas filtram por uma variável de
sessão, setada por transação:

```sql
ALTER TABLE triages ENABLE ROW LEVEL SECURITY;
ALTER TABLE triages FORCE  ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON triages
  USING      (municipality_id = current_setting('app.municipality_id')::bigint)
  WITH CHECK (municipality_id = current_setting('app.municipality_id')::bigint);
```

- `SET LOCAL app.municipality_id = '<id>'` sempre **dentro de transação** — reseta no
  COMMIT/ROLLBACK. `SET` puro persiste na conexão do pool e vaza para o próximo
  request que reusar a conexão.
- `WITH CHECK` impede **gravar** linha de outro tenant, não só ler.
- `FORCE ROW LEVEL SECURITY` é obrigatório: o dono da tabela ignora RLS por padrão e
  o Rails conecta como dono.

**Dois papéis de banco** (`database.yml` declara as duas conexões):

| Papel | Atributo | Usado por |
|---|---|---|
| `rota_app` | sujeito a RLS (FORCE) | caminho web e jobs de domínio |
| `rota_admin` | `BYPASSRLS` | recurring tasks, contexto-operador, migrations — cross-tenant legítimo |

Bypass é por **papel**, não por variável na política (esquecer um `OR` cegaria o
operador; um bug no bypass-var seria permissivo demais). Jobs privilegiados usam
`connected_to(role: :admin)`.

**Tabelas com RLS:** toda tabela com `municipality_id` e dado de tenant — `triages`,
`conversations`, `inbound_messages`, `consents`, `report_snapshots`,
`dashboard_metrics`, `domain_events`, `processed_events`, `protocols`.

**Exceções RLS-exempt (control plane):** `municipality_channels` (estabelece o
tenant — ADR 0007), `users` / `sessions` / `identities` (identidade global —
ADR 0011), `memberships` (autoriza — ADR 0012), `municipalities` (registra o
tenant — ADR 0013). E as tabelas da Solid Queue (`solid_queue_*`): guardam jobs de
todas as cidades — política ali quebraria o despacho. A máquina de fila é
tenant-agnóstica; o **corpo** do job é tenant-scoped.

**Como o tenant é setado — três fontes, um destino (`app.municipality_id`):**

- **Web** — `around_action` em `ApplicationController` resolve o município do
  membership do usuário (ADR 0012) ou do tenant selecionado pelo operador, abre
  transação e faz `SET LOCAL`.
- **Ingestão** — resolvido do `phone_number_id` na borda (ADR 0007).
- **Job** — recebido como argumento literal e aplicado por um concern compartilhado
  (`with_tenant`): ele valida que o `municipality_id` não é nulo (levanta
  `TenantMissing` se for), abre transação, seta `Current.municipality_id`, executa
  `SET LOCAL app.municipality_id` com o valor sanitizado e roda o corpo do job
  dentro dessa transação.

O `municipality_id` **viaja como dado literal** com evento e job (ADR 0004):
descobri-lo consultando o banco já estaria sob RLS — impasse de bootstrap.

## Invariantes

- Nenhuma query de domínio roda sem tenant setado. `rota_app` sem
  `app.municipality_id` faz `current_setting` levantar e a query falhar barulhento —
  **falha fechada**: ausência de tenant nega, não libera.
- Cross-tenant é **explícito**: exige `rota_admin` conscientemente; não há caminho
  acidental.
- `SET LOCAL` só dentro de transação — nunca `SET` puro.
- O control plane é RLS-exempt e protegido **apenas** pela autorização da aplicação
  (ADR 0012); o handoff de gestão de usuários precisa ser à prova de vazamento.

## Consequências

- O isolamento vira **testável no nível do banco**: setar tenant A e tentar ler
  linha de B deve voltar vazio.
- Operação ganha dois papéis / duas conexões; migrations rodam como `rota_admin`.
- `dashboard_metrics` é escopada por política; a visão agregada cross-tenant do
  operador roda sob bypass com `GROUP BY municipality_id`.
- `processed_events` ganha `municipality_id` por consistência; a unicidade segue
  `(event_id, consumer)` — detalhe no ADR 0005.

## Relacionado

- ADR 0004 — `publish` carimba o tenant; `with_tenant` envolve os consumers.
- ADR 0007 — a ingestão resolve o tenant do `phone_number_id` (`municipality_channels`
  é RLS-exempt).
- ADR 0012 — a autorização que protege o control plane.
- ADR 0013 — provisionamento atravessa os dois planos sob bypass.
- ADR 0014 — auditoria platform-scope grava com `municipality_id` nulo sob bypass.
