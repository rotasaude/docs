# ADR 0009 — Protocol engine

- **Status:** Aceita
- **Data:** 2026-06-23
- **Contexto:** Rota Saúde

## Decisão

O coração funcional do Rota Saúde é o protocolo de triagem: uma sequência de
perguntas, validações e decisões que, dado um conjunto de respostas, produz um
desfecho. Protocolos **não são código** — são dados, autorados por equipes clínicas,
versionados e auditáveis. Quatro decisões compõem o subsistema:

1. **Motor puro** — um módulo Ruby sem dependências de Active Record, Active Job ou
   controllers, que dado um Hash devolve um `Protocol` e, dado respostas, devolve um
   `Outcome`.
2. **`Outcome`** — o Value Object imutável que o motor devolve ao chamador.
3. **Storage + façade** — definições vivem no Postgres; uma façade é o único lugar
   que junta o motor puro ao banco.
4. **Scoring** — duas estratégias declaráveis por protocolo (`weighted` e
   `decision_table`).

Um **JSON Schema único** em `contracts/protocols/` (ADR 0002/0015) é o contrato da
definição, compartilhado entre o motor Ruby e o preview no frontend.

**Dois eixos independentes** governam a vida de um protocolo — antes confundidos num
só, agora ambos expressos no campo `status` de uma `protocol_definitions` **per-cidade**:

- **Lifecycle de autoria** (quatro olhos): `draft → in_review → published`. `draft`
  está em escrita (mutável, não ativável); `in_review` está sob os quatro olhos (não
  ativável); `published` foi aprovada pelos quatro olhos (imutável, disponível para
  ativação) — **não** significa "em uso". [ADR 0016: `in_review` deixa de ser
  vestigial e passa a ser o estado em que se assina — entra-se nele por envio
  explícito (`draft → in_review`), e editar uma versão em `in_review` volta a
  `draft`. "Quatro olhos" aqui não é mais o colapso author+publisher do ADR 0012 —
  são duas assinaturas de `protocol_reviewer`s distintos, por ato.]
- **Vigência por cidade:** `published → active` por ativação. `active` é a versão que
  a cidade usa, e exatamente **uma** versão por `(municipality_id, protocol_key)` está
  `active`; `retired` aposenta a versão. **`published ≠ active`**: uma versão pode
  estar `published` (aprovada, disponível) sem estar `active` (em uso). Cidade A pode
  estar `active` na v3 enquanto B está na v2 do mesmo protocolo — versões diferentes
  por cidade são realidade do piloto. A versão `active` é a que **novas** triagens
  daquela cidade consomem.

## Detalhamento

**Motor puro** (`app/protocols/`): `Protocol` (agregado raiz — nome, versão, lista
de `Step`s, config de scoring), `Step` (pergunta + validações + ramificação),
`Validator` (aplica o JSON Schema e gera erros legíveis), `Definitions` (fábrica
Hash → `Protocol`). `Protocol#step(answers)` devolve o próximo `Step`;
`Protocol#evaluate(answers)` percorre o fluxo e devolve um `Outcome`. Ambos aceitam
respostas parciais e nunca levantam por dado faltante — devolvem `:pending` ou um
`Outcome` parcial.

**`Outcome`** — Value Object imutável (o termo é `Outcome` em todo o corpus):

| campo | tipo | semântica |
|---|---|---|
| `status` | `:pending` / `:terminal` | terminou o fluxo? |
| `tier` | String / nil | rótulo clínico (`low`, `medium`, `high`, ...); nil se pendente |
| `priority` | Integer / nil | ordem de atendimento dentro do tier; nil se pendente |
| `trail` | Array<Hash> | `{ step:, answer:, weight: }` na ordem do percurso |
| `awaiting` | Symbol / nil | id do próximo step esperando resposta; só se `:pending` |

Construtores `Outcome.pending(trail:, awaiting:)` e
`Outcome.terminal(trail:, tier:, priority:, score:)`. `to_h` produz Hash JSON-safe,
congelado no `ReportSnapshot` (ADR 0010). O `tier` é String (não enum) por
deliberação — cada protocolo define seu universo; o custo é typo não pegar em
compilação, mitigado pelo lint do JSON Schema.

**Storage — `protocol_definitions` (per-cidade; versão, lifecycle e vigência num só
registro):**

| coluna | tipo | nota |
|---|---|---|
| `protocol_key` | string | qual protocolo (`dengue`, `respiratory`, ...) |
| `version` | integer | monotônico por `(municipality_id, protocol_key)` |
| `municipality_id` | bigint | a cidade dona da definição (**per-cidade**) |
| `status` | enum | `draft` \| `in_review` \| `published` \| `active` \| `retired` |
| `definition` | jsonb | a definição validada via JSON Schema |
| `activated_at` / `retired_at` | timestamptz | — |

Índices: único `(municipality_id, protocol_key, version)`; e **único parcial
`(municipality_id, protocol_key) WHERE status = 'active'`** — só uma versão `active`
por cidade e protocolo. A vigência (`active`) é um **estado da própria definição**
per-cidade, não uma tabela de ponteiro separada. Definições que não passam pelo JSON
Schema **não entram no banco** (validação em `before_save`).

**Façade `Protocols.current` / `Protocols.fetch`** — o único lugar do projeto que
junta o motor puro com o banco. `Protocols.current(municipality_id, protocol_key)`
resolve a definição com `status = 'active'` daquele par e carrega cacheada, com
invalidação no `after_commit` quando o `status` muda. `Protocols.fetch(municipality_id,
protocol_key, version)` busca a versão exata — é o que o relatório histórico (ADR 0010)
usa para carregar a definição usada por uma triagem, mesmo já aposentada.

**Scoring** — duas estratégias em `app/protocols/scoring/`, escolhidas pelo campo
`scoring.type` da definição. A `weighted` soma `step × peso` ao longo do trail e casa
o total contra faixas (thresholds por tier). A `decision_table` confere regras
ordenadas contra o trail — a primeira regra que casa ganha, com um `else` de
fallback. Ambas recebem o **trail completo** como entrada canônica e implementam a
mesma interface mínima (`call(trail) → Outcome` e `to_h` serializável);
`Scoring.build(hash)` é a fábrica que escolhe pela `type`. Misturar as duas num mesmo
protocolo não cabe — seria uma terceira estratégia.

**Lint offline** roda o `Validator` sem Rails nem banco (chama o motor diretamente),
pré-requisito antes de importar uma definição.

**Comandos de lifecycle** — três atos distintos, três entradas de auditoria:

- `PublishProtocol` — **global**; move a versão `in_review → published`; exige role
  `protocol_publisher` + step-up de MFA (ADR 0011/0012); emite `protocol.published`.
  [ADR 0016: só sai de `in_review` — `draft` deixa de ser publicável — e exige duas
  assinaturas de publicação válidas, de `protocol_reviewer`s distintos que não
  editaram a versão, checadas sob lock antes do ato.]
- `ActivateProtocolVersion(municipality_id:, protocol_key:, version:)` — **por
  cidade**; move a versão `published` daquela cidade para `active` (e a anterior
  `active` volta a `published`), operando sobre o campo `status` da definição
  per-cidade; é ato deliberado e auditável, distinto de publicar (R2); emite
  `protocol.activated`. Só uma versão em estado `published` pode virar `active` (R1) —
  ativar `draft`, `in_review` ou `retired` falha. [ADR 0016: exige duas assinaturas de
  ativação válidas, com as suas próprias condições — não servem as assinaturas de
  publicação — e o próprio ato consome as assinaturas, de forma que reativar a mesma
  versão depois pede assinar de novo.]
- `RetireProtocolVersion` — **por cidade**; move uma versão `published` → `retired`.
  Valida que a versão alvo **não está `active`** (R4); se a cidade ainda a tem
  `active`, retorna falha exigindo migrar a cidade para outra versão antes. Nunca troca
  a versão vigente por baixo dos panos — perigoso em contexto clínico.
- `Protocols::RevertActivation` — **por cidade**, novo pelo ADR 0016. Reversão de
  emergência: volta a versão `active` para a que estava em uso imediatamente antes,
  dispensando assinatura (o conteúdo anterior já foi assinado), com step-up e motivo
  obrigatórios; só reverte uma ativação assinada, e reverter uma reversão é recusado.

A separação `published`/`active` só é segura por causa do **congelamento por
snapshot** (R3): uma triagem iniciada sob a versão `active` N **termina em N**, mesmo
que a cidade ative N+1 no meio do fluxo. Essa garantia vem do `ReportSnapshot` por
`protocol_definition_id` (ADR 0010) — sem essa amarração, a ativação de nova versão
não seria segura.

**Eventos do protocolo** (contratos em `contracts/events/`, ADR 0015):

- `protocol.published` — global; uma versão foi aprovada e disponibilizada.
- `protocol.activated` — por cidade; payload
  `{ municipality_id, protocol_key, protocol_definition_id, version, activated_by }`.
- `protocol.retired` — global; uma versão foi aposentada (sob a guarda R4).

## Invariantes

- O motor é **puro**: não importa Rails, não toca banco, não tem efeito colateral;
  todo método é função pura; um `Protocol` instanciado dumpa de volta ao Hash
  original sem perda.
- Definição inválida **erra na construção**, nunca em runtime.
- `evaluate` é função pura do trail e **nunca levanta** por dado faltante (devolve
  `:pending`).
- **Nunca** inspecionar `Outcome.tier` sem checar `status` primeiro.
- `decision_table`: a primeira regra que casa ganha; estável sob ordenação.
- O relatório carrega a definição **exata** usada por uma triagem, mesmo aposentada
  (fidelidade histórica — ADR 0010).
- **INV-protocol-1:** uma versão só vira `active` a partir de `published` — nunca se
  ativa `draft`/`in_review`/`retired`.
- **INV-protocol-2:** exatamente **uma** versão `active` por `(municipality_id,
  protocol_key)` — garantido pelo índice único parcial `WHERE status = 'active'`.
- **INV-protocol-3:** uma triagem termina na versão em que começou (congelamento por
  snapshot); ativar nova versão não afeta triagens em voo.
- **INV-protocol-4:** versão `retired` nunca está `active` (a guarda R4 impede aposentar
  a versão vigente de uma cidade).

## Consequências

- Testabilidade: a suíte do motor roda em milissegundos, sem banco. Portabilidade: o
  mesmo módulo serve o app, o lint offline e (com adaptação TS) o preview no
  frontend — o JSON Schema único é o contrato comum.
- Multi-tenant é **per-cidade**: cada cidade tem suas próprias definições
  (`municipality_id`) e escolhe, pelo campo `status`, qual versão `published` fica
  `active`; cidades distintas rodam versões distintas do mesmo protocolo.
- Mudança no JSON Schema é breaking para definições existentes — exige migração
  versionada por `schema_version` (ADR 0015 governa o versionamento do contrato).
- A façade carrega cacheada: mutação direta no banco (via psql) deixa o app
  inconsistente até reboot.

**RBAC do protocolo.** Os papéis `protocol_author` (cria/edita/submete rascunho) e
`protocol_publisher` (revisa, publica, aposenta) são nomeados aqui mas
operacionalizados como memberships no ADR 0012. **Publicar** (`PublishProtocol`) é ato
global e deliberado: exige step-up de MFA (ADR 0011) e emite `protocol.published`. O
fallback de quatro-olhos é detalhado no ADR 0012. **Ativar** (`ActivateProtocolVersion`)
é ato por-cidade, distinto de publicar — o nível de permissão da ativação (ex.:
`municipal_admin` da cidade) é decidido na aplicação; o comando é separado.
[ADR 0016: o quarto papel do RBAC do protocolo é `protocol_reviewer` — quem assina,
não quem publica nem ativa; publicar e ativar passam a exigir, cada um, duas
assinaturas válidas de revisores distintos, além do step-up e do papel de quem
executa o ato.]

## Relacionado

- ADR 0002 — o JSON Schema vive em `contracts/protocols/`.
- ADR 0004 — `CompleteTriage` chama `evaluate` e publica os eventos da triagem.
- ADR 0010 — o `ReportSnapshot` congela o `Outcome.to_h` e a versão exata da
  definição.
- ADR 0011 — step-up de MFA do publisher.
- ADR 0012 — `protocol_author`/`protocol_publisher` como memberships; quatro-olhos.
- ADR 0013 — protocolo semente no provisionamento da cidade.
- ADR 0016 — assinaturas de dois revisores para publicar e para ativar; `in_review`
  como estado de assinatura; reversão de emergência.

## Em aberto

- **UI de autoria** (formato de edição, fluxo de revisão, preview lado a lado com a
  versão ativa) — deliberadamente adiada; por ora a autoria acontece por script de
  import, com ativação operacional.
- Representar o estado `:aborted` no `Outcome`: hoje a triagem revogada vive como
  `aborted_by_revocation` na `Triage` (ADR 0008), sem estado correspondente no
  `Outcome`.
- Protocolo que precise **mesclar** as duas estratégias de scoring no mesmo fluxo.
